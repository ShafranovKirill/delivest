# Обслуживание и восстановление управляемой франшизы

## Полная копия

Bastion запускает полное копирование раз в сутки в 00:30 UTC, в 03:30 по Москве. Node останавливает целевой Compose-проект и сохраняет PostgreSQL, SeaweedFS, состояние домена витрины и том локальных бэкапов вместе с конфигурацией закреплённого релиза. Если проект работал, Node запускает его до выгрузки. Состояние соседних проектов не меняется. Прерванная выгрузка повторяется с уже сохранённым архивом.

Для managed-архивов нужны внешний S3 bucket и случайный `MANAGED_BACKUP_ENCRYPTION_KEY` длиной от 32 байт в Bastion. Храните этот ключ отдельно от копии Bastion и за пределами исходной ноды. Архив содержит секреты франшизы. Для staging распакованных данных используйте закрытый каталог и удаляйте временные файлы после проверки.

Политика хранения сохраняет последнюю полную копию с подтверждённым восстановлением. Новая выгруженная копия проходит проверку контрольных сумм. Подтверждение восстановления фиксируется после проверки базы и файлов в изолированной среде. Копия после неудачной или незавершённой проверки не заменяет проверенную точку восстановления. Время в поле `captured_at` соответствует моменту полного слепка.

Дамп PostgreSQL в формате `pg_dump -Fc` создаётся без остановки работающей франшизы. Его можно запросить из карточки. Для тестового расписания включите в Bastion `MANAGED_POSTGRES_BACKUP_ENABLED=true`. Интервал составляет четыре часа со сдвигом от ночной полной копии. Срок хранения таких дампов и допустимую потерю заказов нужно определить перед эксплуатацией.

Более свежий дамп PostgreSQL может ссылаться на новые или изменённые медиа после полного слепка. Прежде чем принимать такой дамп как точку восстановления всей франшизы, нужно сверить обязательные объекты с их версиями и содержимым. Полный слепок соответствует одной согласованной точке базы и файлов. Дампы PostgreSQL не участвуют в подтверждении и очистке полных копий.

## Удаление установки

В карточке франшизы остановите размещение и дождитесь подтверждения ноды. Освободите все доменные привязки штатной командой. Для управляемой зоны она удаляет записи, созданные Bastion для этих привязок. Для внешней зоны изменения выполняет её владелец. Затем подтвердите удаление вводом ID франшизы. Node проверяет отсутствие маршрутов и принадлежность томов перед удалением. Bastion сохраняет историю размещения и внешние резервные копии.

## Восстановление

1. В Bastion скачайте полный архив и запишите SHA-256. Если панель недоступна, получите зашифрованный объект из внешнего хранилища, а ключ и контрольную сумму из отдельного хранилища доступа и восстановленного реестра Bastion.
2. Для прямой расшифровки объекта используйте OpenSSL с параметрами ниже. Перед командой загрузите секрет в окружение из хранилища ключей.

   ```sh
   umask 077
   openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
     -in archive.tar.gz.enc -out archive.tar.gz \
     -pass env:MANAGED_BACKUP_ENCRYPTION_KEY
   ```

3. На отдельном Docker-хосте с доступным закреплённым образом PostgreSQL запустите `priv/restore-instance.py` из Delivest Node. Передайте путь к архиву, `--sha256` из реестра и `--output` с новым закрытым каталогом. Команда проверяет контрольную сумму, состав и содержимое архива и создаёт отдельные тома. В `recovery.json` записываются исходные ID, ревизия, релиз, точка восстановления и имена новых томов. Службы и маршруты остаются выключенными.
4. В изолированной среде проверьте миграции, наличие последнего сохранённого заказа и байты связанных файлов, включая приватные объекты. Для проверки приложения нужны локальные адреса, тестовые интеграции и отключённые фоновые обработчики. Зафиксируйте время восстановления и расхождение с последним заказом до сбоя.

Для планового переключения подготовьте и проверьте целевой HTTPS с прежними именами, снимите финальную копию после остановки записи, затем убедитесь, что прежнее размещение недоступно для заказов, вебхуков и фоновых задач. Это ограждение должно переживать перезапуск прежнего сервера. После проверки нового размещения переключите согласованные записи DNS и проверьте оба маршрута в течение TTL. После появления записей на новой базе возврат DNS на старую базу приведёт к разъезду данных.

## Восстановление Bastion

Сохраните независимый PostgreSQL-дамп Bastion вместе с метаданными релиза. Держите `SECRET_KEY_BASE`, `DELIVEST_DNS_ENCRYPTION_KEY` и `MANAGED_BACKUP_ENCRYPTION_KEY` в отдельном защищённом хранилище. Первый ключ нужен для чтения сохранённых паролей, второй для учётных данных DNS, третий для архивов франшиз. Доступ к внешним объектам восстанавливается отдельно.

При проверке дампа в изолированной среде держите HTTP и WebSocket закрытыми, фоновые задачи и интеграции выключенными. До возобновления диспетчеризации сопоставьте незавершённые операции с журналами нод по ID операции и ревизии размещения. Установите фактический результат, прежде чем повторять команду. Сценарий `bastion/scripts/test-recovery.sh` проверяет реестры, размещение, привязки, чтение защищённых данных и восстановление статуса операции из дампа на двух временных экземплярах PostgreSQL.

## Локальная проверка

- В Delivest Node запустите `python3 scripts/test-managed-recovery.py`. Сценарий экспортирует полную копию, удаляет исходный тестовый проект, восстанавливает заказ и связанный объект в свежих томах, проверяет соседний проект и отказ на неверной контрольной сумме. Он также отдельно снимает PostgreSQL-дамп с работающего проекта и импортирует его через `pg_restore`.
- В репозитории Bastion запустите `bash bastion/scripts/test-recovery.sh`. Сценарий использует синтетические записи, PostgreSQL на случайных loopback-портах и работает с выключенным HTTP, без Oban и подключения нод.

В локальном прогоне снимок и остановка синтетического проекта заняли 13,4 секунды. Разворачивание новых томов и проверка заказа № 42, PostgreSQL-дампа и связанного объекта заняли 14,73 секунды. Это замер локального Docker на небольшом наборе данных.

Для приёмки остаётся пилот с двумя франшизами и приложением, входом, тестовым заказом, внешним S3, второй нодой, DNS и HTTPS. Переключение размещения с ограждением исходной ноды и обновление закреплённого релиза с миграциями и проверенным откатом требуют отдельных сценариев. У опубликованного `v1.24.0` есть `release-manifest.json`, а управляемый архив развёртывания появляется в последующей поставке.
