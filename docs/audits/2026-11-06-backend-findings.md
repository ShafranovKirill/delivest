## Evidence and interpretation

Unless stated otherwise, findings below are static source traces. The full backend test suite passed, but broad suite success does not prove these individual cases safe. The shared catalog issue is the only finding here with a new focused runtime reproduction: three ExUnit cases on an isolated test database demonstrated menu leakage, cross-branch stop deletion, and stale cache after a branch-only update. The harness and sanitized result are in [`support/catalog-branch-isolation-repro.exs`](support/catalog-branch-isolation-repro.exs) and [`support/catalog-branch-isolation-repro-result.txt`](support/catalog-branch-isolation-repro-result.txt).

Severity labels are audit triage. Catalog and import authorization impact depends partly on the intended ownership boundary for shared entities; where the source behavior and branch-specific permissions disagree, the report describes the effect and calls out that policy question.

## Findings

### B01 — Shared catalog paths mix global entities with branch-level authorization and state (P1/P2, ownership policy required)

Franchise snapshot import can link one Product/Category record to multiple branches (`server/lib/delivest/site_snapshot/import_plan.ex:218-233`; existing fixture: `server/test/delivest/site_snapshot_franchise_test.exs:254,268,274-277`). `Products.update_product/3` chooses the first related branch for authorization, then changes the single global product row and invalidates/broadcasts only that branch's caches (`server/lib/delivest/net/products.ex:191-207,403-413`). Menu cache entries are branch-keyed (`server/lib/delivest/net/catalogs.ex:5-20`). A staff member authorized for one branch can therefore change data visible through another branch while its cached menu remains stale; the repro verifies both the shared row update and untouched other-branch cache. If branch staff must never edit shared catalog data, treat the cross-branch write as P1. If shared product editing is intended, the ownership/editor policy and cache invalidation still need a global owner or explicit shared-entity policy.

The public menu has a related association-scope issue: categories are selected through the requested branch relation, but the nested product preload filters only active/not-deleted state, not product relation to that branch (`server/lib/delivest/net/categories.ex:11-26`; exposed via `server/lib/delivest/net/catalogs.ex:19-31` and `server/lib/delivest_web/controllers/client/menu/menu_controller.ex:41-49`). The focused runtime case confirmed branch A receives an active product related only to branch B when the category is shared. Cart creation still checks product availability in its branch (`server/lib/delivest/oms/carts.ex:173-224`, `server/lib/delivest/net/products.ex:49-60`); no checkout bypass was confirmed.

Stop state is clearly branch-scoped in its row data but not in its uniqueness/deletion behavior: the unique index is `(product_id, source)` without `branch_id`, while `stop/4` upserts on that key and `resume/3` deletes by product/source without branch (`server/priv/repo/migrations/20261210000004_baseline_catalog.exs:133-143,287-288`; `server/lib/delivest/net/stops.ex:35-76,83-106`). The repro confirmed a branch-B resume removes branch A's manual stop for the same shared product. Existing stop tests cover a single branch only (`server/test/delivest/net/stops_test.exs`).

**Policy distinction:** client identities are installation-global in the current schema, and modifiers/tags are reused across catalog contexts. This audit does not infer that those current scopes are the intended product policy or report the reuse itself as a defect. The confirmed inconsistent paths concern product/category visibility, product mutation/cache ownership, and stop rows, where branch relations, permissions, cache keys, and stop records express conflicting scopes. Record the intended owner and sharing rules for Product, Category, modifiers, tags, and client identity separately before changing those boundaries.

### B02 — Loyalty expiry notice can be permanently skipped after a transient push failure (P2)

`ExpiryNoticeWorker` writes its deduplication/claim row before sending the push and does not check the delivery result (`server/lib/delivest/loyalty/expiry_notice_worker.ex:18-47,50-66`). The sender returns errors, but the push facade suppresses them (`server/lib/delivest/push/sender.ex:27-30`; `server/lib/delivest/push.ex:145-163`). Since the dedupe row remains, a transient provider failure can prevent a retry for that expiry notice. Existing coverage exercises successful delivery, deduplication, and expired tokens, but not transient send failure (`server/test/delivest/loyalty/expiry_notice_test.exs:31-77`). Static finding; not runtime reproduced.

### B03 — Menu CSV export does not neutralize spreadsheet formulas (P2, conditional export risk)

CSV export requires only `products.read` and includes product names and descriptions (`server/lib/delivest/net/menu_export.ex:12-15,26-35`). Cell encoding quotes separators, quotes, and line breaks, but does not neutralize formula-leading characters such as `=`, `+`, `-`, or `@` (`server/lib/delivest/net/menu_export.ex:50-61`). A malicious catalog value may be interpreted as a formula when a recipient opens the CSV in spreadsheet software; interpretation varies by application and settings. Existing controller tests cover ordinary values, not formula prefixes (`server/test/delivest_web/controllers/staff/menu_export_controller_test.exs:13-38`). Static finding; not runtime reproduced.

### B04 — CRM integration LiveView handlers allow write actions after read-only mount authorization (P2)

Frontpad, iiko, and r_keeper integration LiveViews authorize the page mount with `integrations.read`, while several event handlers perform refresh/sync or configuration actions without a corresponding server-side `integrations.update` check. Examples: Frontpad (`server/lib/delivest_web/live/staff/integration_live/frontpad.ex:11,31-58,229-239,640-649`), iiko (`server/lib/delivest_web/live/staff/integration_live/iiko.ex:61-87,202-313`), and r_keeper (`server/lib/delivest_web/live/staff/integration_live/rkeeper.ex:59-67,247-258`). A branch manager preset includes read but not update (`server/lib/delivest/identity/role_presets.ex:32-40`), so a connected read-only staff member can invoke an event that the UI may hide. Side effects include external catalog refresh and local snapshot writes (`server/lib/delivest/integrations/crm/catalog.ex:21-29,72-80`), provider stop sync (`server/lib/delivest/integrations/crm/stop_sync.ex:9-18,44-62`), and iiko webhook/settings updates (`server/lib/delivest/integrations/iiko.ex:116-117`; `server/lib/delivest/integrations/iiko/api.ex:90-114`). Existing tests use update/admin permissions and do not assert denial for read-only event callers (`server/test/delivest_web/live/staff/integration_live/frontpad_test.exs:17-151`; `server/test/delivest_web/live/staff/integration_live/iiko_test.exs:13-18`). Static authorization finding; no forged event was run.

### B05 — Menu import permission is weaker than the mutations it performs (P2)

`MenuImport.apply` checks `products.create` (`server/lib/delivest/net/menu_import.ex:43-46`) but can update existing products, hide existing products absent from the import, and mutate categories/modifiers (`:63-64,91-191`). A role with create but without update can therefore perform catalog edits beyond its declared permission. Static finding; no create-only-role test was found.

### B06 — Phone-confirmation throttle check can race concurrent starts (P2 hardening candidate; exploitability unconfirmed)

`PhoneConfirmations.throttle/2` counts recent rows for phone/session, then the call flow contacts the provider and inserts a confirmation in separate operations (`server/lib/delivest/identity/phone_confirmations.ex:32-66`; call path `server/lib/delivest/identity/client_auth.ex:25-30`, controller `server/lib/delivest_web/controllers/client/auth/auth_controller.ex:27-40`). Concurrent requests can each observe a count below the configured threshold and proceed before either inserts, exceeding the per-phone/session request limit. The code does not appear to atomically reserve a slot. Existing tests cover sequential cases only; no concurrency-specific test or runtime reproduction was performed. Treat as a race hardening concern, not a confirmed bypass exploit.

### B07 — Yandex Eda order intake may check availability against stale stop data (P2 freshness risk)

The incoming order path synchronously calls `OrderIntake.ensure_available/…` before order creation (`server/lib/delivest/integrations/yandex_eda/order_intake.ex:22-43`; entry points: `server/lib/delivest/integrations/yandex_eda.ex:220-221` and `server/lib/delivest_web/controllers/integrations/yandex_eda/order_controller.ex:9-20`). Stop refresh waits up to `max(2s, CRM interval + 1s)` but its timeout/failure is not used to fail closed; the code checks existing local stop records instead (`server/lib/delivest/integrations/yandex_eda/stop_list.ex:26-55`). The stop-sync freshness timestamp advances only on successful provider fetch (`server/lib/delivest/integrations/crm/stop_sync.ex:44-67`). A stale local snapshot can therefore accept an order for a product that has since become unavailable. Existing tests cover fresh cache/disabled paths, not refresh failure with stale data (`server/test/delivest/integrations/yandex_eda/stop_list_test.exs:8-23`). Static finding; not runtime reproduced.

### B08 — Yandex Eda order intake performs Dadata geocoding synchronously (P2 latency risk)

`OrderAddress.build` calls Dadata before `Oms.create_order` (`server/lib/delivest/integrations/yandex_eda/order_attrs.ex:14-23`; `server/lib/delivest/integrations/yandex_eda/order_address.ex:8-23`; `server/lib/delivest/integrations/dadata/api.ex:16-27`). The default HTTP receive timeout is 15 seconds (`server/lib/delivest/HTTP/client.ex:6,30-35,60-62`), adding provider latency directly to the inbound order request. Dadata errors fall back to an empty geocode rather than failing the intake; the existing flow retains the provider-supplied address coordinates, so this finding concerns request latency rather than confirmed coordinate loss. This is separate from the core customer checkout delivery quote, which the earlier scoped pass verified is local-only. Static trace; latency was not measured.

### B09 — YooKassa reconciliation reports success after its pagination cap (P2 reconciliation completeness risk)

Reconciliation fetches pages of 100 up to 50 pages and returns the accumulated result at the cap without confirming there is no next cursor (`server/lib/delivest/integrations/yookassa/reconciliation.ex:13-15,111-132`). The caller compares a 48-hour local set to that truncated remote set (`:44-75`). Above 5,000 remote records in that window, local payments corresponding to later remote pages may be reported as missing remotely, and unknown remote payments can be omitted from the comparison. This is an incomplete audit/false-alert risk, not evidence of lost or duplicated money. Static finding; no volume or runtime test evidence.

### B10 — r_keeper polling can occupy a default-queue worker for a long batch (P2 operational scaling risk; upper bound only)

The poller loads active confirming/sent orders and performs provider requests sequentially (`server/lib/delivest/integrations/rkeeper.ex:233-278`). The API's default wait is 30 seconds and HTTP timeout is wait plus 10 seconds (`server/lib/delivest/integrations/rkeeper/api.ex:7-23,49-55`); the worker uses the shared default Oban queue (`server/lib/delivest/integrations/poller/worker.ex:1-5`). In the provider-timeout case, a batch of N orders can take up to roughly N×40 seconds and occupy one default-queue worker, reducing queue capacity for other jobs according to configured concurrency. This is a code-path upper bound, not a measured production observation. No poller runtime/performance test was run.

### B11 — Concurrent courier cash settlements can create a stale, empty settlement (P2 financial operations integrity)

`Cash.settle/3` calculates the balance before starting its transaction (`server/lib/delivest/couriers/cash.ex:25-33,36-47`). Inside the transaction it inserts a settlement using that snapshot, then marks currently open payments with the new settlement ID without checking how many rows were updated (`:36-47,91-96`). If two authorized settlements for the same courier overlap, both can snapshot the same payments; the second transaction may insert a settlement with the stale amount after the first has already attached the payments, then update zero payments while still returning success. Existing coverage is sequential (`server/test/delivest/couriers/cash_test.exs:64-79`); no concurrent settlement test or runtime reproduction was run. Static finding.

### B12 — Custom analytics date ranges are unbounded and materialized per day (P2 authenticated resource-exhaustion risk)

`resolve_period("custom", from, to, branch_id)` parses arbitrary dates, swaps reversed endpoints, and applies no maximum duration (`server/lib/delivest/analytics.ex:14-41`). The Statistics LiveView accepts that range from URL/filter params, then loads multiple period queries and materializes every day using `for date <- Date.range(from, to)` (`server/lib/delivest_web/live/staff/statistics_live/index.ex:19-38,66-79`; `server/lib/delivest/analytics.ex:84-108`). A staff account with `statistics.read` can request a very large range, making repeated queries span a long history and allocating a date row per day. Existing tests cover presets and a short custom range, not a duration bound (`server/test/delivest/analytics_test.exs:147-158`). Static finding; no resource-exhaustion attempt or runtime measurement was performed.
