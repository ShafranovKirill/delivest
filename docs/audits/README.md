# Аудит Delivest — 6 ноября 2026

## Краткое резюме

Аудит исходников и доступных проверок завершён в рамках описанных ниже границ. Крупные исправления в этом проходе не выполнялись; добавлены audit-документы и изолированное воспроизведение проблемы каталога. Результаты не являются сертификатом отсутствия других дефектов.

Самый высокий риск — несовпадение общей модели каталога с правами и branch-scoped состоянием: обновление общего продукта может затронуть несколько филиалов, публичное меню включает связанный с другим филиалом продукт, а остановку можно снять из другого филиала. При политике строгой изоляции каталога это P1; фактическое владение товарами и категориями требует продуктового решения.

## Приоритеты

1. **P1/P2 — общий каталог и изоляция филиалов.** Уточнить владельца Product/Category и поведение shared catalog. Если сотрудники филиала не должны менять общий продукт, ограничить запись; согласовать с этим меню, кэш и остановки. Три проявления воспроизведены в изолированном тесте.
2. **P2 — авторизация, данные и финансовая точность.** Исправить event-handler ACL в CRM LiveViews и mismatch прав меню-импорта; проверить сохранение адреса между сессиями и races подтверждения auth/cart. Для кассового расчёта курьеров добавить сериализацию параллельных операций. CSV-экспорт должен обезвреживать spreadsheet formulas.
3. **P2 — интеграции и аналитика.** Разобрать потерю push-уведомлений при временной ошибке, stale stop-list и синхронный запрос DaData в Yandex Eda, неполную YooKassa сверку после лимита страниц, длительный serial polling r_keeper и неограниченный пользовательский диапазон статистики. Большинство этих выводов статические; поведение и частота не измерялись.
4. **P2 — backup и выпуск.** Исправить застревание backup job после ошибки начальной записи статуса и перестроить выпуск так, чтобы GitHub release не публиковался до успешной сборки всех образов.
5. **P2/низкий — клиентский UX и доступность.** Проверить stale delivery quote перед оформлением, асинхронные ошибки корзины, неправильный маршрут корзины, клавиатурные действия карточки/плитки и часовой пояс баннера.

## Границы

- Frontend: напрямую прочитаны все 258 ручных файлов `client/src`; найденные клиентские проблемы статические, браузерно для каждой не воспроизводились.
- Backend: в инвентаре 641 `server/lib` модуль и 200 тестовых файлов; прямо прочитан заявленный набор доменных путей и отдельная выборка 100 web-файлов (25 LiveViews, 55 controllers, 20 channels/hooks/plugs). Остальные backend-модули не читались построчно.
- Agent/deploy/CI: напрямую прочитаны все 23 `agent/lib` файла, все три workflow, deploy nginx template и host installer script, а также три корневых скрипта. Deploy и production операции не выполнялись.
- Test suite результаты подтверждают запуск suite целиком, но не опровергают статические условия, для которых отдельный кейс не написан.

## Следующие шаги

- Сначала зафиксировать правила владения и редактирования каталога в multi-branch установке.
- Для P1/P2 findings добавить целевые проверки на отрицательные роли, параллельные запросы, сбои провайдера и смену филиала/сессии.
- Перестроить workflow выпуска так, чтобы GitHub release отражал только полностью опубликованный набор image артефактов.
- После выбора политики и очередности оформить изменения отдельными небольшими PR; в этом проходе изменения исходников не вносились.
