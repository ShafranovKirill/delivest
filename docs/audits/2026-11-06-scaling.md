# Scaling and backend audit — 2026-11-06

> Кратко: backend выглядит подходящим основанием для умеренной нагрузки при пяти филиалах; локальный benchmark не задаёт production capacity. Главные практические риски — рост очереди CRM при лимитах провайдера, незавершённое исправление изоляции клиентских сессий, stale lock в agent и отсутствие CI-контроля дрейфа OpenAPI. F01–F10 в основном требуют новых bounded contexts и миграций; для F01 следует добавить отдельную сегментацию аудитории и переиспользовать rewards/promotions как механизм предложения.

### Local order-create benchmark

Command, after creating and migrating a new isolated partition:

```sh
MIX_ENV=test MIX_TEST_PARTITION=_capacity_bench_v5_20261106 mix ecto.create
MIX_ENV=test MIX_TEST_PARTITION=_capacity_bench_v5_20261106 mix ecto.migrate
MIX_ENV=test MIX_TEST_PARTITION=_capacity_bench_v5_20261106 mix run ../docs/audits/support/order-create-bench.exs
```

The script uses the existing test factory, five local branches, pickup/cash orders, and no external providers. It explicitly refuses to run unless `MIX_ENV=test` and the dedicated benchmark partition are set. It warms up 50 orders, then creates 250 orders with concurrency 10. Result: **250/250 succeeded**, 0.642 seconds elapsed, p50 22.62 ms, p95 46.67 ms, 9,000 Repo queries (36 per order), aggregate Repo query time 5,241.67 ms, aggregate Repo queue time 174.45 ms; 300 orders and five branches were present afterward. Sanitized result: `docs/audits/support/order-create-bench-result.txt`; original run log: `/tmp/delivest-capacity-bench-results-v5.log`.

Telemetry query/queue measurements are native Erlang time units. The harness now converts with `System.convert_time_unit(value, :native, :nanosecond) / 1_000_000` before labeling the totals as milliseconds. Earlier values labeled as milliseconds were invalid and must not be used. This microbenchmark is evidence about the in-process domain path on this local database and machine only; it excludes HTTP, real provider latency, TLS, production database/network topology, steady-state worker backlog, contention at 50 orders/minute, and multi-node behavior. The observed short run must not be extrapolated into a capacity figure.

## Findings

### Backend

**B1 — CRM delivery throughput is intentionally asynchronous, but can backlog on a shared Frontpad account (operational scaling risk, medium).**

Order create stores the order and its domain event in one `Ecto.Multi` transaction (`server/lib/delivest/oms/orders/create.ex:23-82`). The event subscriber enqueues CRM work after that transaction (`server/lib/delivest/integrations/crm/order_subscriber.ex:25-44`); provider HTTP happens in the worker (`server/lib/delivest/integrations/crm/sync_worker.ex:20-28`). Therefore CRM response time does not hold the order-create transaction open. The `:crm` Oban queue has concurrency 2 (`server/config/config.exs:10-15`). Frontpad uses a 2,000 ms throttle interval keyed by API key (`server/lib/delivest/integrations/frontpad.ex:90,121-123`); reservation uses local Cachex and returns a throttle delay immediately (`server/lib/delivest/integrations/crm/throttle.ex:6-12,35-46`), which the worker snoozes rather than sleeping in a queue slot (`server/lib/delivest/integrations/crm/sync_worker.ex:67-69`). This permits at most 30 starts/minute per key per BEAM node, before provider latency constraints. With two workers and 15-second provider calls, the concurrency ceiling would be about 8 calls/minute (`2 * 60 / 15`), subject to measured latency and retries. If sustained demand is 50 orders/minute routed to one Frontpad key, even the ideal 30/minute throttle implies a queue growing by at least 20/minute. This is not a synchronous order-create limit; monitor queue age/backlog and provider duration. The Cachex limiter is node-local, so replicas do not share a cluster-wide limit.

**B2 — Order create has 36 Repo calls/order in the local benchmark; suitable for the stated modest target, but measure production-like contention before setting a capacity ceiling (low).**

The single atomic domain path includes client resolution, cart acquisition, fulfillment/schedule/price/stop/delivery checks, number allocation, order insert, payments/loyalty/events, and cart detach (`server/lib/delivest/oms/orders/create.ex:29-71`). The local instrumented run observed 36 Repo queries per created order. At 50 creates/minute that is approximately 30 queries/second by multiplication, not a measured production rate. Production Repo defaults to pool size 10 and has `pool_count` commented out (`server/config/runtime.exs:94-100`). The order path's delivery calculation is inside the DB transaction (`server/lib/delivest/oms/orders/create.ex:52-54`), but inspected `Delivery.quote` reads local branch zones/settings and performs local geometry (`server/lib/delivest/oms/orders/delivery_fee.ex:19-31`; `server/lib/delivest/delivery.ex:118-120`); it does not call Yandex Delivery. No external network call was found in the core `Oms.create_order` path. The public online checkout can call YooKassa **after** create/transaction (`server/lib/delivest_web/controllers/client/order/order_controller.ex:53-60,230-245`; `server/lib/delivest/payments/online.ex:290-307`), with HTTP receive timeout 15 seconds (`server/lib/delivest/HTTP/client.ex:6,26-34`). This provider wait is not part of the measured domain benchmark.

**B3 — Per-node rate limits and one-node OTP configuration limit horizontal guarantees (medium only if scaling across nodes).**

The generic rate-limit plug uses local Cachex (`server/lib/delivest_web/plugs/rate_limit.ex:7,20-34`; Cachex child in `server/lib/delivest/application.ex:22-33`). No distributed counter or cluster coordination was found in this pass. Current single-node/modest deployment can use it as configured; adding replicas would multiply effective limits unless the limiter is made shared or traffic is partitioned. Oban PostgreSQL notifier/jobs provide durable DB-backed job distribution, but no multi-node cluster configuration was found in the inspected application tree. This is a scale-out qualification, not a blocker at five branches on one node.

**B4 — No confirmed tenant/branch IDOR or unsafe payment transition in reviewed paths.**

Client cart/order mutation and reads check ownership against the client/session; channel subscriptions bind to the signed client token and order owner (`server/lib/delivest_web/controllers/client/cart/cart_controller.ex:430-435`; `server/lib/delivest/oms/carts.ex:59-69`; `server/lib/delivest/oms/orders.ex:96-120,172-203`; `server/lib/delivest_web/channels/client_socket.ex:10-18`; `server/lib/delivest_web/channels/orders_channel.ex:8-11`). Online payment updates lock and transact state (`server/lib/delivest/payments/online.ex:39-59,281-287`), and YooKassa request idempotency uses payment/refund identifiers (`server/lib/delivest/integrations/yookassa/api.ex:10-24,48-56`). This is a positive scoped review, not a proof over every endpoint.

**B5 — Modular monolith boundaries and atomic outbox are a solid base.**

Order creation is behind `Oms.create_order` and composed from named domain steps; outbox/domain-event rows and Oban jobs are inserted in the same transaction (`server/lib/delivest/events.ex:17-31,40-51`). Integration contexts use provider behaviors and facades (e.g. `server/lib/delivest/integrations/crm/provider.ex:14-69`, `server/lib/delivest/integrations/crm.ex:43-58,163-179`). No direct `Repo` calls were found in controllers or channels in the scoped search; the few reviewed LiveView transaction boundaries call domain functions. `lifeline`, `pruner`, and `crontab` in top-level Oban config are accepted by the pinned Oban version; they are not a configuration defect.

### Client and agent findings supplied by the parent and checked against the shared worktree

**C1 — Auth refresh/session cache isolation (P1, addressed in client PR).** The client changes isolate private query keys by identity, clear them on logout/sign-in, and bind refresh flights to the session epoch/token (`client/src/modules/auth/private-query-cache.ts:8-31`; `client/src/modules/auth/stores/auth.store.ts:33-43`; `client/src/modules/auth/api/auth-session.js:1-35`; `client/src/modules/auth/api/auth-interceptor-core.ts:37-76`). Regression tests cover stale 401 responses, logout during refresh, and account switching (`client/tests/auth-session-isolation.test.mjs:77-193`). Root reports fix commit `89b7e05` is in [PR #13](https://github.com/ShafranovKirill/delivest-web/pull/13), `pnpm test:auth` passed 7/7, and the client build passed with existing Vite chunk/environment warnings. Tests exercise Axios wiring; socket-token coverage is a test helper, not browser E2E. This audit did not run client checks or independently confirm the P1 impact assessment.

**A1 — Agent directory lock can remain stale after process/VM termination (P2, recoverability issue).** `OperationLock.with_lock/2` creates `.delivest-operation.lock` as a directory, removes it only in an `after` block, and returns “busy” if it already exists (`agent/lib/delivest_agent/operation_lock.ex:4-27`). A process kill or machine crash bypasses the `after`, leaving future operations blocked until manual cleanup. Current test explicitly confirms that an existing lock is preserved and reported busy (`agent/test/delivest_agent/full_backup_test.exs:74-87`), but does not cover stale-owner recovery. Keep automatic removal conservative: a lock may belong to a live concurrent process; add ownership/expiry or explicit operator recovery with tests before changing behavior.

**C2 — OpenAPI drift prevention is not wired into CI (documentation/client-contract gap, low to medium).** Backend OpenAPI is derived from router paths (`server/lib/delivest_web/openapi.ex:6-19`) and exposed at `/api/openapi` (`server/lib/delivest_web/router.ex:21-24,482-485`). Client has `schema:download`, `schema:generate`, and `schema:sync` scripts (`client/package.json:17-19`; root `Makefile:88`), but download targets `http://localhost:4000`; repository CI search found no schema sync/diff check. The checked-in `client/src/api/docs/swagger.json` can therefore lag server schemas/routes without CI failure. No particular stale operation/schema was established in this pass, so this is a drift-detection gap rather than a proven runtime contract bug.

## Reviewed areas and limits

Reviewed backend areas: order and cart creation, delivery pricing, online payment initiation/webhooks, event outbox and subscribers, CRM provider/throttle/sync worker, Frontpad unknown-outcome classification, auth and ownership checks, client socket/channel subscriptions, Oban and Repo runtime config, schema/migration inventory, and the feature matrix areas. Also checked client auth refresh/cache worktree, agent operation lock and its test, OpenAPI generation scripts and CI files. No application code was changed; this report and the reproducibility support files are the only repository additions by this subtask. Existing shared `client` submodule changes were preserved.

Limitations: no production DB, replica, provider credentials, external order/payment, mobile application, browser E2E, or deployment load test was used. The local benchmark uses a fresh test DB and test app configuration; it does not model real DB hardware, cache state, slow providers, queue saturation, many concurrent branches, or an HTTP request path. The feature matrix identifies currently visible backend primitives and gaps; it does not assert product acceptance criteria beyond the supplied F01–F10 labels. Further audit passes should verify any suspected endpoint-specific authorization edge cases and generated-contract freshness if a concrete runtime mismatch is reported.

## Suggested phased delivery

1. **P1 client session isolation:** review PR #13 containing the auth refresh/cache fix; root reports `pnpm test:auth` passed 7/7 and build passed with existing Vite chunk/environment warnings; then add owner-isolation tests for every private query/socket cache. Keep refresh across account switches covered.
2. **Operational reliability:** add stale lock ownership/recovery semantics to the agent with conservative liveness checks; add a CI check that regenerates/downloads the OpenAPI schema from the same build and fails on a diff. Avoid silently deleting ambiguous live locks.
3. **Modest production capacity evidence:** run a staging-like test at the intended 50 orders/minute across five branches with realistic order mix, DB sizing, events enabled, and provider mocks with realistic latency; separately test CRM backlog drain and Frontpad per-key rate limits. Record p95/p99, Repo queue time, DB pool waits, Oban queue age, and error rates. Do not extrapolate the local benchmark into a capacity ceiling.
4. **F01–F10 in small vertical PRs:** start with product-facing foundations that touch existing boundaries—F03 slot reservation and F05 ledger-backed referral are transactional/data-model work; F04 attribution/outbox extends events; F01 adds a separate audience/segmentation context and calls existing promo/reward mechanics to create and redeem offers; F02 review and F06 onboarding add separate bounded contexts; F07/F08/F09/F10 are larger operational/domain projects. Each PR should state invariants, API contracts for web and React Native, migration plan, idempotency, and tests before implementation.
5. **Database and mobile rollout:** use additive migrations first (nullable/new tables/indexes), deploy code that tolerates old and new data, backfill in bounded batches, then enable behavior behind flags per branch. Keep rollback as a feature-flag disable plus code rollback while additive schema remains; perform destructive cleanup only in a later release after old app versions/mobile clients have aged out. Publish/update the generated API schema in the same PR and retain old response fields during the mobile compatibility window.
