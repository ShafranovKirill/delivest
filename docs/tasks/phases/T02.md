# T02 — Права записи и финансовая целостность

**Статус:** planned. **Источник:** [архив рефактора](../sources/refactor-spec.md), [архив функций](../sources/features-spec.md). **ID:** D05–D09.

## Цель и граница

Server CRM LiveView/application facade, menu import, courier cash, phone/stats; client лишь сопряжённые формы.

Основные блоки по ID: D05/D08 → S2, D06 → S1, D07 → S3, D09 → S4. Статус каждого ID обновляется только в этой primary карточке и COVERAGE.

## Зависимости и шаги

T00; независимые критичные PR можно начинать до закрытия T01.

Серверные проверки каждого side effect, import capability, сериализация settlement и проверка присвоения платежей; адресовать phone/stats по исходным критериям.

## Приёмка и доказательства

Read-only actor не пишет во внешнюю систему; create-only не обновляет через import; конкурентный settlement создаёт одну фактическую проводку; отрицательные сценарии D08/D09.

## Миграция и откат

Для новых constraints — backfill и проверка конфликтов; обратимый rollout, reconcile финансовых записей перед откатом.
