# T12-F03 — Вместимость слотов и управление загрузкой

**Статус:** planned. **Первичный ID:** F03-R01, F03-R02, F03-R03, F03-R04, F03-R05, F03-R06, F03-R07, F03-A01, F03-A02, F03-A03, F03-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f03).

## Цель и граница

Реализовать вертикаль F03 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Расписание, жизненный цикл заказа и оплаты; F07 для последующей связи с курьерскими ресурсами. Capacity/logistics; решение о hold, времени квоты и конкуренции до миграции. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F03-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F03-A01, F03-A02, F03-A03, F03-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
