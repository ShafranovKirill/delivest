# T12-F06 — Подключение заведения и диагностика интеграций

**Статус:** planned. **Первичный ID:** F06-R01, F06-R02, F06-R03, F06-R04, F06-R05, F06-R06, F06-R07, F06-R08, F06-A01, F06-A02, F06-A03, F06-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f06).

## Цель и граница

Реализовать вертикаль F06 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Существующие адаптеры и журналы. Это также часть предстартовой проверки всех новых функций. S4 adapters/diagnostics; сквозная диагностика начинается раньше вертикали. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F06-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F06-A01, F06-A02, F06-A03, F06-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
