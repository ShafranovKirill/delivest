# T12-F01 — Сегменты клиентов и кампании возврата

**Статус:** planned. **Первичный ID:** F01-R01, F01-R02, F01-R03, F01-R04, F01-R05, F01-R06, F01-R07, F01-A01, F01-A02, F01-A03, F01-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f01).

## Цель и граница

Реализовать вертикаль F01 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

F04 — модель событий и атрибуция; существующие бонусы, промо и уведомления. S1 каталог/цены и F04 event foundation в marketing/events серии; согласие/каналы и durable effects. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F01-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F01-A01, F01-A02, F01-A03, F01-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
