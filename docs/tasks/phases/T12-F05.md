# T12-F05 — Реферальная программа

**Статус:** planned. **Первичный ID:** F05-R01, F05-R02, F05-R03, F05-R04, F05-R05, F05-R06, F05-R07, F05-A01, F05-A02, F05-A03, F05-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f05).

## Цель и граница

Реализовать вертикаль F05 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Бонусы, идентификация клиента, промо; F04 для измерения. Marketing/events после identity, бонусов и F04 attribution. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F05-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F05-A01, F05-A02, F05-A03, F05-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
