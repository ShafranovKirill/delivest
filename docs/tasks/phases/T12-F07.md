# T12-F07 — Автоназначение курьеров, объединение заказов и маршруты

**Статус:** planned. **Первичный ID:** F07-R01, F07-R02, F07-R03, F07-R04, F07-R05, F07-R06, F07-R07, F07-A01, F07-A02, F07-A03, F07-A04, F07-A05. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f07).

## Цель и граница

Реализовать вертикаль F07 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Готовность заказа и F03; достоверные курьерские статусы/геопозиция. Capacity/logistics после пилота и выбора маршрутизации. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F07-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F07-A01, F07-A02, F07-A03, F07-A04, F07-A05 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
