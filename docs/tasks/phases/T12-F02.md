# T12-F02 — Отзывы после заказа и обработка проблем

**Статус:** planned. **Первичный ID:** F02-R01, F02-R02, F02-R03, F02-R04, F02-R05, F02-R06, F02-R07, F02-A01, F02-A02, F02-A03, F02-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f02).

## Цель и граница

Реализовать вертикаль F02 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

События завершения заказа, уведомления, роли и права; F01 для общих частотных ограничений. Marketing/events после основ обратной связи и уведомлений. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F02-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F02-A01, F02-A02, F02-A03, F02-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
