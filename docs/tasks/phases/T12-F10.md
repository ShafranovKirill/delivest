# T12-F10 — Сохранённый способ оплаты

**Статус:** planned. **Первичный ID:** F10-R01, F10-R02, F10-R03, F10-R04, F10-R05, F10-R06, F10-R07, F10-R08, F10-A01, F10-A02, F10-A03, F10-A04, F10-A05. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f10).

## Цель и граница

Реализовать вертикаль F10 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Текущая интеграция оплаты, идентификация клиента, идемпотентность и модель продавца. Saved payment вместе с payment context после T03/T10 и выбора провайдера. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F10-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F10-A01, F10-A02, F10-A03, F10-A04, F10-A05 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
