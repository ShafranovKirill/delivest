# T12-F09 — Печать и устойчивость рабочего места при сбоях связи

**Статус:** planned. **Первичный ID:** F09-R01, F09-R02, F09-R03, F09-R04, F09-R05, F09-R06, F09-R07, F09-R08, F09-A01, F09-A02, F09-A03, F09-A04, F09-A05. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f09).

## Цель и граница

Реализовать вертикаль F09 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

POS, кухня, события заказа, права. Выбор оборудования и границы полного офлайна остаются открытыми решениями. Print после выбора оборудования и сценария пилота. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F09-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F09-A01, F09-A02, F09-A03, F09-A04, F09-A05 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
