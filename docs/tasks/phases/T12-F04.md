# T12-F04 — Воронка заказов и источники привлечения

**Статус:** planned. **Первичный ID:** F04-R01, F04-R02, F04-R03, F04-R04, F04-R05, F04-R06, F04-R07, F04-R08, F04-A01, F04-A02, F04-A03, F04-A04. Полные требования и критерии: [исходный раздел](../sources/features-spec.md#f04).

## Цель и граница

Реализовать вертикаль F04 через UI → API → домен → storage → интеграции → тесты. Сначала подтвердить фактические точки входа в T00; сохранять branch/network isolation, права, идемпотентность и честные состояния из общих требований источника. Область PR ограничивать модулями этой вертикали и её явно названными зависимостями.

## Зависимости и решения

Основа измерения F01/F05; существующие отчёты и события заказов. Event foundation совместно с F01; полный отчёт после согласования атрибуции. Открытые продуктовые/контрактные решения взять из [DECISIONS](../DECISIONS.md) и соответствующего раздела источника до изменения схемы/API. Доменные блоки оптимизируют повторное использование контекста, не меняют исходный бизнес-приоритет F01–F10.

## Шаги, приёмка и evidence

Разбить на проверяемые PR: контракт и данные, доменный сценарий, UI/операторский путь, отказ/повтор и rollout. Для каждого требования F04-Rxx сохранить связь с изменением и тестом в [coverage](../COVERAGE.md). Критерии F04-A01, F04-A02, F04-A03, F04-A04 выполнить в точной формулировке источника. Запустить целевые unit/integration/e2e/contract тесты на выбранных SHA; внешние и аппаратные проверки отметить отдельно, если недоступны.

## Миграция, откат и checkpoint

Схему вводить поэтапно с backfill/совместимым чтением, feature flag и отключением без потери истории; для платежей, печати и внешних операций отдельно сверять неизвестный исход. После проверенного PR записать SHA, команды, результат и следующий шаг в [handoff](../SESSION_HANDOFF.md); не помечать всю функцию done по одному частичному PR.
