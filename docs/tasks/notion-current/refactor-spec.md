## 1. Цель и исходные ограничения

Подготовить существующий модульный монолит Phoenix/Elixir к надёжной работе, росту числа покупателей, развитию F01–F10 и будущему React Native. Сохранить действующие сценарии заказов, оплаты, кухни, POS, курьеров и интеграций. Устранить найденные ошибки границ филиалов, прав, конкурентных операций и восстановления после сбоев.

Исходный профиль владельца: до 5 филиалов; ориентир до 50 заказов в минуту суммарно; меню до 200 позиций, изменения ориентировочно до 3 раз в день. Число активных посетителей и характеристики production-сервера пока не определены. Редкость изменений меню не распространяется автоматически на стоп-лист, паузы и доступность.

Вместимость по числу клиентов пока не измерена. Ступени 100/500/1000 одновременно активных сессий — план испытаний, не обещание обслуживания. Ограничение throughput Frontpad исключено владельцем из целевых расчётов данного этапа; сохраняются требования к идемпотентности, неизвестному результату и диагностике интеграции. Не повышать лимиты провайдера ради теста.

Микросервисы, новый брокер очередей, Redis, отдельный процесс GenServer на каждую доменную сущность и полное переписывание не являются исходными требованиями. Базовый стек: Phoenix, PostgreSQL, Ecto, Oban, Cachex. Каждый новый компонент должен иметь измеренную причину.

## 3. Полный реестр найденного и критерии исправления

Для каждой записи: завести проверяемое изменение с данным ID; сохранить источник, отрицательный/аварийный сценарий и результат теста. Статическое заключение подтвердить целевым тестом до изменения; при опровержении обновить статус с доказательством.

<b>Требование и приёмка:</b> Установить владельца общей сущности и полномочия; отклонять запись вне разрешённой области либо требовать явное общее право; инвалидировать все затронутые филиалы. Отрицательный role-тест + проверка обоих меню. Runtime подтверждено.

## 4. Целевая архитектура и обязательные инварианты

### R01 — модульный монолит и DDD

Оставить контексты с явным владельцем данных: каталог/доступность, корзина/расчёт, заказы, платежи/фискализация, лояльность/промо, доставка, identity/ACL, интеграции, уведомления. UI, REST и workers вызывают application facade. Провайдеры скрываются за behaviours/adapters; единые внутренние DTO/errors и capabilities отражают реально доступные операции.

Критерии: новые правила не дублируются в Vue, LiveView, RN и отдельных адаптерах; контроллеры не реализуют бизнес-транзакции; существующие bulk Repo.transaction из LiveView при затрагивании переносятся в application use cases. OTP-процессы применяются для concurrency/isolation/runtime state, доменная организация остаётся модулями/функциями.

### R02 — короткая транзакция до ответа об успешном заказе

Под блокировкой/optimistic version проверить владельца, филиал и версию корзины; серверно подтвердить цену/доступность/расписание; атомарно применить бонусы и лимиты промо; записать снимок состава и цены, заказ, события и фоновые задачи; затем commit и ответ.

Ключ идемпотентности привязан к клиентской операции и области владельца. Повтор с тем же payload возвращает тот же результат; иной payload с тем же ключом получает определённый conflict. Закрепить invariant ограничениями БД, а не только job uniqueness. Конкурентные запросы не создают два заказа/списания/погашения.

После commit «заказ сохранён» не означает «оплачен», «принят рестораном» или «доставлен в CRM». Состояния должны явно различаться.

Перенос самого создания заказа в фон не входит в базовый вариант. Если измерения потребуют его, отдельный ADR: durable checkout request, 202 Accepted, polling/event updates, reservation expiry, eventual rejection и компенсации. Не показывать окончательный успех до фиксации заказа.

### R03 — существующий transactional outbox и Oban

Переиспользовать Events/Oban: запись business state + event/jobs в одной транзакции; rollback не оставляет внешнюю задачу. Сейчас CRM и push уже фоновые; не создавать второй параллельный механизм.

Вынести тяжёлые side effects с request path: доставка CRM, push/уведомления, фискальные операции и обогащение. Post-commit PubSub/preload профилировать; при переносе обеспечить durable постановку и свежую выдачу по API, не считать best-effort broadcast источником истины.

Каждый обработчик допускает at-least-once delivery: idempotent бизнес-операция, durable status, attempts/backoff/deadline, ручное разрешение unknown outcome. Job unique не гарантирует однократность внешнего эффекта. Если worker упал после remote success до local commit, повтор сверяется по устойчивому идентификатору.

Приёмка: kill/restart до/после commit и remote call, повторные события и timeout не теряют заказ и не дублируют бизнес-операцию. Очерёдность изменений одного aggregate сохраняется либо проверяется версией; старое событие не откатывает новый статус.

### R04 — изоляция очередей и перегрузка

Разделить по назначению и SLA: создание платёжной сессии, CRM delivery/commands, status polling, fiscal, notifications, тяжёлые служебные работы. Конкурентность определить измерениями и ограничениями провайдера. Одного механического увеличения concurrency недостаточно.

Добавить backlog size/oldest age, длительность и ошибки, dead-letter/manual resolution, контроль retry storms. Когда очередь не успевает, показывать реальное состояние и деградацию; не принимать неограниченную работу без мониторинга. Backup/thumbnail/backfill не вытесняют критические операции.

### R05 — асинхронная подготовка оплаты: отдельный проектируемый шаг

Сейчас checkout после order commit синхронно вызывает ЮKassa. Проект варианта: payment\_initializing → awaiting\_confirmation → paid/failed/expired; worker создаёт сессию с idempotency key, UI получает ссылку через API/событие и показывает ожидание с ограниченным временем.

До реализации определить expiry заказа, бонусов и промокода, повтор запроса ссылки, отмену, неизвестный исход, открытие на другом устройстве и возврат из provider/deep link. События кухни/CRM отправляются только в разрешённой фазе; order.created при awaiting\_payment сейчас специально отложено, это поведение нельзя случайно сломать. ЮKassa тестовый контур и сценарии duplicate webhook обязательны.

### R06 — меньше повторного SQL, единый расчёт

Профилировать отдельно cart mutation/read и order create: число/время запросов по шагам, повторяющиеся SELECT, N+1, транзакции и ожидания pool.

Один request-scoped набор товаров/вариантов/модификаторов обслуживает pricing, строки заказа, earnings и rewards. Сейчас эти этапы повторно читают товары; Promo.Engine дополнительно refresh-ит product refs при каждом расчёте несмотря на compiled cache. Объединить чтения пакетно по уникальным IDs/slugs, сохранить category/snapshot поля и серверную проверку. Не пропускать проверки лимитов/баланса ради уменьшения счётчика SQL.

Повторно использовать уже заблокированную корзину; проверить необходимость отдельных lock/existing-order/view/metadata reads. Защиту от повторного заказа и актуальность promo\_code/gifts сохранить.

<b>Цель первого этапа:</b> снижение на 10–20% относительно сопоставимого baseline 36 SQL, то есть ориентировочно 29–32 SQL/заказ. Это плановая цель, не прогноз и не достигнутый результат. 200–350 SQL/мин экономии при 50 заказах/мин — округлённая иллюстрация достижения этой цели, не production-замер. Для сложного состава/бонусов число может отличаться. Приёмка сравнивает также p95, CPU, DB time/queue waits, а не один счётчик.

### R07 — версии, кеш и меню

Menu cache уже существует; при до 200 позициях и редких изменениях это не первый кандидат сложного масштабирования. Исправить branch selection/invalidation, кешировать публичное представление по branch/catalog\_version; ETag/conditional GET и предварительное заполнение пяти филиалов проверить как следующие оптимизации.

Отделить редко меняющийся каталог от оперативной доступности, стопов, пауз и расписаний. У каждой зависимости ясные version/TTL/invalidation и fallback при Cachex failure. При shared entity инвалидируются все затронутые branch caches. Не добавлять общий Redis без измеренной необходимости.

Кешировать compiled promo rules и справочные product refs с версией каталога. Не считать cached usage count/loyalty balance разрешением на списание: окончательная проверка и изменение атомарны в PostgreSQL.

Cart расчёт может иметь ключ branch/client-or-guest/cart\_version/catalog\_version/promo\_version плюс остальные фактические зависимости, включая время правила. TTL не заменяет инвалидирование. Не кешировать персональный расчёт под общим ключом. Персональные данные очищаются/разделяются по identity; запросы старой эпохи не меняют новое состояние.

Приёмка: изменение цены/промо/доступности/клиента/филиала/временного окна не возвращает чужой или устаревший расчёт; cold cache и сбой кеша сохраняют корректность.

### R08 — единый API для web и React Native

OpenAPI текущей сборки — проверяемый контракт: CI regeneration/drift detection, совместимые DTO, error codes, pagination, money в согласованных единицах, UTC timestamps + branch timezone, idempotency и cart versions.

RN использует те же application use cases и бизнес-правила. Native-specific secure storage, deep links/платёжный возврат, push/device token lifecycle, reconnect/resync проектируются явно. События помогают обновить экран, API остаётся источником восстановления после пропуска событий. Версионирование payload событий и окно совместимости мобильных версий обязательны.

## 5. Нагрузочная приёмка и измеряемые цели

### N01 — профиль

Базовый прогон: 5 филиалов, 200 позиций на филиал, варианты/модификаторы, несколько применимых и неприменимых промо, guest/account, доставка/самовывоз, бонусы, наличные/онлайн. Не заменять реалистичное меню одним товаром. Общая целевая интенсивность заказов — 50/мин; отдельно всплески и холодный кеш. Фоновые очереди работают и измеряются, а не остаются неразобранными.

Ступени 100 → 500 → 1000 активных сессий, затем до найденного предела, с реальным think time и долями menu/cart/checkout/auth/socket действий. Например, действие раз в 10 секунд даёт 10/50/100 HTTP req/s для этих ступеней; это модель действий, не вместимость. Меню просто открытой вкладки не равно постоянно активному клиенту.

Провайдеры сначала мокируются с измеримой задержкой, ошибками, 429, timeout и unknown outcome; live sandbox отдельно в разрешённых пределах. Frontpad throughput в capacity-цели не включать по решению владельца. Тесты не создают production-платежей/заказов.

### N02 — методика

До оптимизации зафиксировать CPU/RAM/диск, сеть, версии БД/BEAM, pool size, worker concurrency, dataset, seed, sha и cache state. Повторить идентичный профиль после изменений минимум три раза.

Предлагаемые длительности для первого плана испытаний: прогрев 5 минут, стабильная ступень 30 минут, всплеск 5 минут, затем длительный прогон не менее 2 часов на рабочей ступени. Длительности — проект теста, не уже выполненная проверка. Интервалы и SLO уточняются до запуска; не снижать критерии задним числом ради «успеха».

Измерять: p50/p95/p99 HTTP menu/cart/checkout отдельно, server-domain latency без provider wait, RPS, технические 5xx/timeouts, бизнес-отказы отдельно, SQL count/time/queue\_time/lock wait, pool saturation, CPU/RAM/GC, socket count/disconnect/resync, worker duration/retry/backlog age и время восстановления.

### N03 — предварительные критерии для согласования перед запуском

Проект технических SLO: p95 тёплого меню ≤200 мс, cart action ≤300 мс, сохранения заказа без provider wait ≤500 мс на выбранном окружении; технические 5xx/timeouts \<0,1% на стабильной ступени. Эти значения — предложенные критерии приёмки, не доказанные характеристики и не договорный SLA.

Нулевой допуск: потерянные подтверждённые заказы, дубли списаний/погашений/создания, межфилиальные/межпользовательские утечки. На стабильной ступени backlog/память не растут неограниченно; после всплеска очередь возвращается к baseline в заранее заданный бюджет. Бюджеты зависят от класса очереди и доступности провайдера; установить до теста.

Вместимость публикуется только как максимальная подтверждённая ступень на конкретном окружении, с mix/actions/think time и запасом для эксплуатации. Экономия SQL не переводится автоматически в такой же процент роста клиентов. Процент роста устойчивости не выдумывать: публиковать результаты аварийных сценариев и recovery time.

### N04 — аварийные проверки

- Crash до commit: нет заказа и не должно быть внешних задач.
- Crash после commit: заказ доступен, задачи восстановимы.
- Crash после remote success: повтор не дублирует операцию.
- Duplicate/reordered webhook, двойное нажатие, retry HTTP, concurrent последняя квота/промо/бонус/settlement.
- Недоступны CRM, push, cache, БД/исчерпан pool; slow query, retry storm, polling backlog.
- Switch branch/account во время запросов; reconnect после пропущенных событий.
- Ошибка диска/status.json, stale lock, незавершённое обновление агента, частичная публикация images.

## 6. Миграции, совместимость и порядок работ

### Этап A — инварианты и регрессионные тесты

D01–D09, C01–C05: владение shared catalog, филиальные выборки/стопы, роли, импорт, деньги курьера, race auth/cart/phone, персональные данные. Сначала negative/concurrent tests; доказательные «bug exists» harness преобразовать в желаемые expectations после исправления.

### Этап B — профиль SQL и критический путь

### Этап C — интеграции, эксплуатация и качество интерфейса

D10–D15, O01–O09, C06–C10: retries, stop freshness, reconciliation completeness, polling, backup/release/CI, CSV, честные capabilities, UX/accessibility/timezone. Не отложить критический permission/financial дефект до performance-этапа.

### Этап D — нагрузка, пилот и подключение F01–F10

N01–N04; затем контролируемый пилот поддерживаемых комбинаций. Каждый общий механизм принимается до функций, зависящих от него; не требуется переписать весь проект до первой вертикальной функции.

Для схемы стопов/общих сущностей: inventory существующих shared links/rows → решение ownership → additive schema/backfill bounded batches → dual-compatible code при необходимости → проверки → поэтапное включение. Не разносить конфликтующие исторические данные наугад. Откат: флаг/совместимая версия кода при сохранении истории; destructive cleanup позже. Отдельный restore drill резервной копии.

Все изменения в codex/\* от актуального develop, отдельные небольшие Conventional Commits/PR; подмодули коммитятся первыми, затем gitlink. Сохранять чужие изменения, без force push. Review главного агента и реальные результаты проверок обязательны. Релиз в main после gates, production только из main; наличие ТЗ не запускает deploy.

Предыдущее исключение native apps из F01–F10 сохраняется как граница того продуктового набора; текущее ТЗ отдельно добавляет архитектурную готовность к RN, не заявляя реализацию мобильного приложения.

## 8. Definition of Done и открытые решения

- [ ] Каждый ID реестра имеет disposition: исправлен и проверен / опровергнут с доказательством / принятое ограничение с владельцем решения. Нельзя закрывать статическую гипотезу одним зелёным общим suite.
- [ ] Зафиксирован ADR ownership shared catalog, глобальных клиентов/modifiers/tags, branch prices/stops.
- [ ] Не нарушены сценарии создания → оплаты → CRM → кухни → получения и отмены/возврата/чека.
- [ ] Выполнены negative ACL, concurrent, retry/crash, cache/version и UI regression checks для затронутого поведения.
- [ ] Схема/API/events совместимы с актуальными web/mobile версиями; OpenAPI drift и auth tests в CI.
- [ ] Есть воспроизводимые SQL before/after, load/fault отчёты, ограничения окружения и подтверждённая вместимость.
- [ ] Все provider/hardware/live checks имеют честный статус: проведён/не проведён/не применим.
- [ ] Протестированы миграции и восстановление/откат; мониторинг показывает stale/incomplete/unknown состояния.
- [ ] Реестр находится в одном месте и связан с исходным ТЗ F01–F10; сроки/исполнители не выдуманы.
