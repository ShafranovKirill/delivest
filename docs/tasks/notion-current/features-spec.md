<b>1. F01 — Сегменты клиентов и кампании возврата</b>

<b>Цель.</b> Дать заведению управляемый инструмент возвращения гостей и возможность оценивать результат действий.

<b>Что уже есть / что проверить.</b> Есть клиентские карточки, история заказов, бонусы, промо и Web Push. Сегменты, адресные кампании и полный цикл их измерения ранее не обнаружены. Существующее напоминание об истечении бонусов нужно переиспользовать, не дублировать.

<b>Основной сценарий.</b> Маркетолог выбирает «не заказывали более заданного числа дней», видит размер аудитории, создаёт предложение, проверяет сообщение, запускает кампанию и затем видит результаты.

<b>Функциональные требования</b>

- <b>F01-R01.</b> Сегменты: новые гости, первый завершённый заказ, давно не заказывали, постоянные гости. Пороги дней, числа заказов и периода настраиваются; определения показываются пользователю. Доступ ограничен сетью и разрешёнными филиалами.
- <b>F01-R02.</b> Редактор кампании: название, аудитория, сообщение, ссылка на витрину/предложение, канал из доступных, предварительный просмотр, тестовая отправка сотруднику, время запуска в заданном часовом поясе.
- <b>F01-R03.</b> Перед запуском показывать доступную аудиторию и исключения: нет разрешения на канал, нет доступного адресата, частотный лимит, исключённый клиент. Повторно проверять допустимость отправки непосредственно перед доставкой.
- <b>F01-R04.</b> Статусы: черновик, запланирована, выполняется, приостановлена/отменена, завершена. Повтор фоновой задачи не должен повторно отправлять одно и то же сообщение адресату.
- <b>F01-R05.</b> Второй шаг: автоматические сценарии после первого заказа и периода неактивности. Выход из сценария после нового заказа; частотные ограничения между кампаниями. Триггеры истечения бонусов согласовать с существующим механизмом.
- <b>F01-R06.</b> Отчёт: выбранные/исключённые адресаты, отправки, подтверждённая доставка только при наличии сигнала провайдера, переходы, связанные заказы, выручка и затраты бонусов. Окно атрибуции показывать явно; наблюдаемая выручка не равна доказанному приросту.
- <b>F01-R07.</b> Использовать существующий движок скидок/бонусов. Многоканальные цепочки, произвольный визуальный конструктор и полный RFM можно отложить. Контрольную группу предусмотреть как следующий этап оценки эффекта.

<b>Критерии приёмки</b>

- [ ] <b>F01-A01.</b> На подготовленной базе сегменты выбирают ожидаемых гостей; отменённые заказы учитываются согласно явно заданной политике.
- [ ] <b>F01-A02.</b> Гость без разрешения на выбранный канал исключается; повтор запуска и повтор доставки задачи не создают дублей сообщений.
- [ ] <b>F01-A03.</b> После нового заказа клиент не получает устаревшее предложение «вернуться», если сценарий предусматривает выход.
- [ ] <b>F01-A04.</b> Отчёт объясняет значения и окно атрибуции; отказ канала виден оператору, недоступные метрики не выдумываются.

<b>Где появится в продукте.</b> Клиенты → Сегменты; Маркетинг → Кампании; карточка кампании → результаты.

<b>Зависимости.</b> F04 — модель событий и атрибуция; существующие бонусы, промо и уведомления.

<b>Где посмотреть и что изучить</b>

- [STARTER: ресторанное решение](https://starterapp.ru/solutions/restaurant) — Изучить RFM, сегменты и триггерные рассылки. Это описание поставщика, не спецификация его внутренней реализации.
- [eDA: уведомления](https://eda-platform.ru/functional/notifications) — Посмотреть аудитории и каналы клиентских уведомлений.

<b>2. F02 — Отзывы после заказа и обработка проблем</b>

<b>Цель.</b> Замкнуть цикл «заказ → обратная связь → реакция сотрудника → решение», замечать повторяющиеся проблемы филиалов.

<b>Что уже есть / что проверить.</b> Есть входящая обратная связь Яндекс Еды. Собственный сбор оценки после заказа и единая очередь решения проблем ранее не обнаружены. Автозагрузка публичного рейтинга Яндекса — отдельная незавершённая функция, её не смешивать с этим модулем.

<b>Основной сценарий.</b> После завершения заказа гость получает приглашение оценить опыт. При проблеме сотрудник видит связанный заказ, назначает ответственного и фиксирует решение.

<b>Функциональные требования</b>

- <b>F02-R01.</b> Настройки запроса оценки по филиалу: включение, задержка после завершения заказа, канал и частотный лимит. Не отправлять запросы по отменённым заказам.
- <b>F02-R02.</b> Короткая форма: общая оценка, комментарий и категории проблемы — еда, доставка, комплектация, другое. Детальные оценки категорий допустимы как последующее расширение.
- <b>F02-R03.</b> Одна обратная связь на заказ с согласованным правилом редактирования. Ссылка не раскрывает чужие заказы, контакты или платёжные данные; срок действия и доступ гостя определить при проектировании.
- <b>F02-R04.</b> Очередь обращений: фильтры филиала, периода, оценки, категории, ответственного и статуса. Статусы: новое, в работе, решено. Порог проблемной оценки настраивается.
- <b>F02-R05.</b> Карточка связывает отзыв, заказ и клиента с учётом прав. Сотрудник фиксирует внутреннюю заметку, связь с гостем и результат. Компенсации только отдельным разрешённым действием через существующие механизмы.
- <b>F02-R06.</b> Показывать время реакции, долю ответивших и повторяющиеся причины проблем. Не публиковать внутренние комментарии сотрудников.
- <b>F02-R07.</b> Публичная лента отзывов и внешние площадки не входят в первый выпуск. Если позже появится внешнее приглашение, не фильтровать его только по положительным оценкам.

<b>Критерии приёмки</b>

- [ ] <b>F02-A01.</b> Завершённый заказ получает один запрос; повторное событие завершения не дублирует отправку.
- [ ] <b>F02-A02.</b> Низкая оценка создаёт видимое обращение с правильным заказом и филиалом.
- [ ] <b>F02-A03.</b> Недоступный канал не ломает заказ; проблема отправки диагностируется.
- [ ] <b>F02-A04.</b> Изменение ответственного и статуса сохраняется в истории; сотрудник без прав не видит чужую область данных.

<b>Где появится в продукте.</b> Страница оценки гостя; Заказы → Обратная связь; карточка обращения; настройки филиала.

<b>Зависимости.</b> События завершения заказа, уведомления, роли и права; F01 для общих частотных ограничений.

<b>Где посмотреть и что изучить</b>

- [STARTER: ресторанное решение](https://starterapp.ru/solutions/restaurant) — Посмотреть заявленные отзывы после заказа и работу с обратной связью.
- [Foodeon: доставка](https://foodeon.com/ru/delivery) — Посмотреть сценарий обратной связи руководству; не считать маркетинговую страницу доказательством конкретного workflow.

<b>3. F03 — Вместимость слотов и управление загрузкой</b>

<b>Цель.</b> Не обещать гостю время, которое заведение не сможет выдержать, и предлагать ближайшую доступную альтернативу.

<b>Что уже есть / что проверить.</b> Предзаказ, расписание, специальные часы, паузы и выбор времени уже есть. В ранее просмотренной логике не найдены квоты нагрузки по временному интервалу.

<b>Основной сценарий.</b> У филиала заполнен интервал самовывоза. Гость видит его недоступность и выбирает следующий; отмена заказа освобождает зарезервированную нагрузку по согласованным правилам.

<b>Функциональные требования</b>

- <b>F03-R01.</b> Настраиваемые интервалы и лимиты по филиалу, дню и способу получения. Для первого выпуска считать заказы; расчёт по трудоёмкости блюд — отдельное расширение.
- <b>F03-R02.</b> Разделять время готовности и время получения/доставки. Явно определить, к какому времени относится квота и как учитываются ASAP-заказы.
- <b>F03-R03.</b> При заполнении предлагать следующий доступный интервал. Соблюдать существующие рабочие и специальные часы, часовой пояс филиала и ручную паузу.
- <b>F03-R04.</b> Согласовать момент резервирования и срок удержания места при ожидании онлайн-оплаты. Отмена, истечение резерва и поздний платёж обрабатываются без отрицательной или бесконтрольной вместимости.
- <b>F03-R05.</b> Проверять доступность при финальном подтверждении заказа, а не только в интерфейсе. Одновременные покупатели не могут занять одно последнее место.
- <b>F03-R06.</b> Оператор видит загрузку и может изменить лимит или сделать разрешённое исключение с причиной. Уже принятые заказы при уменьшении лимита не теряются.
- <b>F03-R07.</b> Определить учёт заказов из POS, админки и внешних каналов: должны влиять на реальную нагрузку, но отклонять внешние заказы можно только в рамках контракта канала. Политику подтвердить на следующем этапе.

<b>Критерии приёмки</b>

- [ ] <b>F03-A01.</b> При одновременной попытке занять последнее место квота не превышается.
- [ ] <b>F03-A02.</b> Отмена/истечение освобождает резерв ровно один раз; повторные события безопасны.
- [ ] <b>F03-A03.</b> Проверены полночь, особые часы, пауза, смена дня в часовом поясе филиала.
- [ ] <b>F03-A04.</b> Гость получает объяснение и альтернативу; изменение лимитов не удаляет принятые заказы.

<b>Где появится в продукте.</b> Настройки филиала → Загрузка и слоты; выбор времени заказа; экран загрузки оператора.

<b>Зависимости.</b> Расписание, жизненный цикл заказа и оплаты; F07 для последующей связи с курьерскими ресурсами.

<b>Где посмотреть и что изучить</b>

- [STARTER: подготовка к праздникам](https://starterapp.ru/journal/get-ready-for-the-holidays) — Изучить интервалы, предзаказы и настройки приготовления. Источник не доказывает наличие полного механизма квот.
- [Смартомато: автораспределение](https://help.smartomato.ru/hc/user-guide/articles/auto-dispatch) — Изучить будущие заказы и отложенный запуск диспетчеризации.

<b>4. F04 — Воронка заказов и источники привлечения</b>

<b>Цель.</b> Показать заведению, откуда приходят заказы и на каком этапе гости прекращают оформление.

<b>Что уже есть / что проверить.</b> Продажи и операционная отчётность есть. Связка источника посещения с шагами оформления и итогом заказа ранее не обнаружена.

<b>Основной сценарий.</b> Владелец сравнивает источники трафика и видит, что после расчёта доставки часть гостей покидает оформление; проверяет эффект изменения условий.

<b>Функциональные требования</b>

- <b>F04-R01.</b> Словарь событий: просмотр меню, просмотр товара при необходимости, добавление в корзину, начало оформления, выбор получения, создание заказа, подтверждённая оплата, отмена и завершение.
- <b>F04-R02.</b> Сохранять UTM и источник в рамках согласованной модели атрибуции. Показать различия прямых визитов, неизвестного источника и недоступных данных.
- <b>F04-R03.</b> Разделять созданные, оплаченные и выполненные заказы. Для наличных/офлайн-оплаты не применять платёжный шаг так, будто онлайн-оплата обязательна.
- <b>F04-R04.</b> Дедупликация событий и устойчивость к повторным вебхукам/перезагрузке страницы. Подтверждение оплаты брать из достоверного серверного состояния.
- <b>F04-R05.</b> Отчёт по периоду, филиалу, устройству при доступности данных и источнику: посетители/сессии согласно выбранному определению, переходы по шагам, конверсия и заказы.
- <b>F04-R06.</b> Интеграция с выбранной внешней аналитикой через явные события. Не строить собственный универсальный аналог систем веб-аналитики.
- <b>F04-R07.</b> Не передавать контакты, адрес доставки и другие лишние персональные данные в аналитические события. Согласовать разрешения, срок хранения и окно атрибуции.
- <b>F04-R08.</b> Связать кампании F01 и приглашения F05 с событиями без двойного суммирования выручки.

<b>Критерии приёмки</b>

- [ ] <b>F04-A01.</b> Тестовый путь от UTM до заказа сохраняет источник; обновление страницы не удваивает покупку.
- [ ] <b>F04-A02.</b> Отказ онлайн-оплаты не учитывается как оплаченный заказ; наличный заказ корректно отображается в своей воронке.
- [ ] <b>F04-A03.</b> Отчёт позволяет объяснить расхождения между сессиями, заказами и платежами.
- [ ] <b>F04-A04.</b> При блокировке внешней аналитики оформление продолжает работать.

<b>Где появится в продукте.</b> Аналитика → Воронка; Источники; настройки внешних аналитических систем.

<b>Зависимости.</b> Основа измерения F01/F05; существующие отчёты и события заказов.

<b>5. F05 — Реферальная программа</b>

<b>Цель.</b> Дать гостям понятный способ приглашать друзей и измерять новые заказы от рекомендаций.

<b>Что уже есть / что проверить.</b> Бонусный учёт уже есть. Связка приглашения, первого выполненного заказа и награждения участников ранее не обнаружена.

<b>Основной сценарий.</b> Гость делится ссылкой, новый клиент оформляет первый заказ; после выполнения заказа начисляется предусмотренное правилами вознаграждение.

<b>Функциональные требования</b>

- <b>F05-R01.</b> Персональный код/ссылка, экран «пригласить друга», описание условий и история доступных пользователю наград.
- <b>F05-R02.</b> Настройки области действия программы: сеть/филиалы, порог заказа, вознаграждение сторонам, срок акции, лимиты приглашений и совместимость с другими предложениями.
- <b>F05-R03.</b> Однозначное правило нового клиента и закрепления пригласившего. Участие проверять серверно; спор нескольких кодов разрешать согласно показанному правилу.
- <b>F05-R04.</b> Начисление по подтверждённому событию выполнения и выбранному условию оплаты. Отмена/возврат обрабатываются обратной проводкой по согласованной политике, не удалением истории.
- <b>F05-R05.</b> Не допускать самоприглашения и повторного вознаграждения за один первый заказ. Предусмотреть лимиты и очередь подозрительных операций без автоматических наказаний по единственному слабому признаку.
- <b>F05-R06.</b> Отчёт: приглашения, новые клиенты, первые выполненные заказы, сумма наград, отмены наград. Применять существующий журнал бонусов.
- <b>F05-R07.</b> Зафиксировать нерешённую политику частичного возврата и случая, когда бонус уже потрачен.

<b>Критерии приёмки</b>

- [ ] <b>F05-A01.</b> Два одинаковых события выполнения дают одну награду.
- [ ] <b>F05-A02.</b> Существующий клиент не получает награду нового по установленным правилам; самоприглашение отклоняется.
- [ ] <b>F05-A03.</b> Отмена до выполнения не начисляет награду; возврат выполняет согласованную коррекцию.
- [ ] <b>F05-A04.</b> Клиент и оператор видят причину начисления/отказа, а аудит связывает награду с приглашением и заказом.

<b>Где появится в продукте.</b> Личный кабинет → Пригласить друга; Маркетинг → Реферальная программа; отчёт и журнал наград.

<b>Зависимости.</b> Бонусы, идентификация клиента, промо; F04 для измерения.

<b>Где посмотреть и что изучить</b>

- [STARTER: решение для пиццерий](https://starterapp.ru/for-whom/pizza) — Изучить заявленную реферальную программу и её место в маркетинге.
- [FoodSoul: настройки бонусов](https://wiki.foodsoul.ru/ru/public/info/settings/bonuses_settings) — Посмотреть описанные бонусные/реферальные настройки; конкретные правила Delivest сформулированы в этом ТЗ отдельно.

<b>6. F06 — Подключение заведения и диагностика интеграций</b>

<b>Цель.</b> Довести подключение до проверенного первого заказа и сократить число проблем, для решения которых нужен разработчик.

<b>Что уже есть / что проверить.</b> Есть импорт меню, настройки филиалов, адаптеры ресторанных систем, журналы и диагностика. Требуется сначала сопоставить существующие экраны с целевым сценарием, затем закрыть пробелы; не создавать второй независимый центр диагностики.

<b>Основной сценарий.</b> Ответственный проходит настройки, видит непроверенные этапы, проводит контролируемый проверочный заказ и получает подтверждение, что статусы и оплата работают.

<b>Функциональные требования</b>

- <b>F06-R01.</b> Пошаговый маршрут: заведение и филиал; витрина; меню и сопоставления; зоны/график; способы оплаты; ресторанная система; уведомления; чек при применимости.
- <b>F06-R02.</b> У каждого шага разделять «настроено», «проверено», «ошибка», «не применимо». Наличие ключа не означает исправную интеграцию.
- <b>F06-R03.</b> Проверочный сценарий заказа с явным выбором тестовой/боевой среды. Не создавать реальные платежи или фискальные операции скрытно.
- <b>F06-R04.</b> Показывать возможности выбранного адаптера: что поддерживается для отправки, правок, отмены, меню и статусов; объяснять ограничения до выполнения действия.
- <b>F06-R05.</b> Единый список затронутых заказов и проблем: провайдер, филиал, время, последнее успешное действие, состояние, разрешённый следующий шаг. Переиспользовать имеющиеся health и журналы.
- <b>F06-R06.</b> Для неизвестного исхода отправки: сверка с внешней системой, привязка найденного внешнего заказа, разрешённая повторная отправка только после проверки отсутствия дубля. Сохранять автора и результат решения.
- <b>F06-R07.</b> Автоматические повторы только для безопасных случаев; недоступность внешней системы не должна выглядеть как успешное подтверждение.
- <b>F06-R08.</b> Передавать заведению итоговый список проверенных сценариев и оставшихся ограничений. Данные доступа в отчёты не включать.

<b>Критерии приёмки</b>

- [ ] <b>F06-A01.</b> Неисправная интеграция не получает статус «проверено» только из-за заполненных настроек.
- [ ] <b>F06-A02.</b> Тайм-аут с неизвестным исходом виден оператору и разрешается без неконтролируемого повторного создания заказа.
- [ ] <b>F06-A03.</b> Для неподдерживаемой операции пользователь видит понятное ограничение.
- [ ] <b>F06-A04.</b> Повторное открытие мастера сохраняет прогресс; изменение критичных настроек помечает зависимую проверку устаревшей.

<b>Где появится в продукте.</b> Подключение заведения; Настройки интеграций; Проблемы заказов; карточка проблемного заказа.

<b>Зависимости.</b> Существующие адаптеры и журналы. Это также часть предстартовой проверки всех новых функций.

<b>Где посмотреть и что изучить</b>

- <mention url="https://app.notion.com/p/3e931ec95e44805fb97ac7d80efe6664">Delivest</mention> — Разделы «Интеграции» и «Маршрутизация заказов»: исходное описание текущего поведения.
- [Смартомато: интеграция Frontpad](https://help.smartomato.ru/hc/user-guide/articles/int-pos-frontpad) — Посмотреть пользовательское объяснение настройки интеграции. Мастер и состояния готовности здесь — предложение для Delivest, а не установленная копия интерфейса конкурента.

<b>7. F07 — Автоназначение курьеров, объединение заказов и маршруты</b>

<b>Цель.</b> Сократить ручную диспетчеризацию и улучшить предсказуемость исполнения заказов при собственной доставке.

<b>Что уже есть / что проверить.</b> Есть собственные курьеры, назначения, геопозиция и диспетчерская. Оптимизация маршрутов ранее не найдена; полноту существующего назначения уточнить на следующем этапе.

<b>Основной сценарий.</b> Диспетчер видит рекомендованного курьера с объяснением; затем включает автоматический режим для подходящих заказов и при необходимости вмешивается.

<b>Функциональные требования</b>

- <b>F07-R01.</b> Этап 1 — рекомендация кандидатов по доступности, загрузке, смене, транспорту и времени до точки при наличии достоверных данных.
- <b>F07-R02.</b> Этап 2 — автоназначение с возможностью ручного изменения, фиксируемой причиной решения и защитой от назначения одного заказа двум курьерам.
- <b>F07-R03.</b> Учитывать будущие заказы и предполагаемую готовность; не вызывать курьера слишком рано без объяснимой политики.
- <b>F07-R04.</b> Батчинг: объединять только совместимые доставки с ограничениями по числу заказов, времени и обещанным срокам. Показать последовательность остановок и влияние добавления заказа.
- <b>F07-R05.</b> ETA и предупреждения о риске опоздания с отметкой времени обновления. Устаревшую или отсутствующую геопозицию не выдавать за точную.
- <b>F07-R06.</b> Переназначение при отказе/недоступности курьера; видимый сценарий «подходящего курьера нет». Ручное управление остаётся доступным.
- <b>F07-R07.</b> Выбор картографического/маршрутного провайдера и стоимость обращений — решение следующего этапа. Не обещать математически оптимальный маршрут без согласованного критерия.

<b>Критерии приёмки</b>

- [ ] <b>F07-A01.</b> Недоступный или перегруженный курьер не назначается вопреки установленным правилам.
- [ ] <b>F07-A02.</b> Конкурирующие действия оператора и автоматики не создают двойного назначения.
- [ ] <b>F07-A03.</b> Диспетчер может понять причину назначения и безопасно изменить его.
- [ ] <b>F07-A04.</b> При отказе маршрутизатора остаётся ручной сценарий; ETA обозначен как недоступный/устаревший.
- [ ] <b>F07-A05.</b> Полевой сценарий нескольких заказов подтверждает соблюдение ограничений, а не только отображение маршрута на карте.

<b>Где появится в продукте.</b> Диспетчерская; настройки автоназначения; маршрут курьера; журнал решений.

<b>Зависимости.</b> Готовность заказа и F03; достоверные курьерские статусы/геопозиция.

<b>Где посмотреть и что изучить</b>

- [STARTER Логист](https://starterapp.ru/logist) — Посмотреть автоназначение, батчинг, маршруты и работу курьера; рекламные показатели экономии не переносить в обещания Delivest.
- [Смартомато: автораспределение](https://help.smartomato.ru/hc/user-guide/articles/auto-dispatch) — Изучить ограничения нагрузки, режимы распределения и будущие заказы.
- [Смартомато: отслеживание](https://help.smartomato.ru/hc/user-guide/articles/courier-tracking) — Посмотреть отображение статуса и информации доставки гостю.

<b>8. F08 — Комбо-конструктор и пицца из половинок</b>

<b>Цель.</b> Дать пиццериям и заведениям с наборами корректный путь от конфигуратора до кухни и ресторанной системы.

<b>Что уже есть / что проверить.</b> Варианты товаров, группы модификаторов и промо уже есть. Специализированные половинки и конфигурируемые наборы ранее не обнаружены; не подменять существующие модификаторы новым параллельным механизмом.

<b>Основной сценарий.</b> Гость выбирает размер и две совместимые половины пиццы либо наполняет комбо из разрешённых групп; видит доплаты и окончательную цену.

<b>Функциональные требования</b>

- <b>F08-R01.</b> Настройки наборов: группы выбора, допустимые товары/варианты, минимальное и максимальное количество, обязательность и доплаты.
- <b>F08-R02.</b> Половинки: общие размер/основа, допустимые сочетания, выбранные половины, политика добавок. Формулу цены определить явно: фиксированная, доплаты или иной согласованный вариант.
- <b>F08-R03.</b> Показывать итоговый состав и изменение цены до добавления в корзину. Сервер пересчитывает стоимость и проверяет доступность.
- <b>F08-R04.</b> Учитывать стоп-лист каждого компонента. Если компонент исчез, объяснить замену; не подменять состав молча.
- <b>F08-R05.</b> Сохранять снимок выбранного состава в заказе, чтобы изменение меню не меняло историю. Повтор заказа проверяет текущую доступность и цены.
- <b>F08-R06.</b> Передавать состав в кухню, POS и интеграцию так, чтобы персонал мог приготовить заказ. Для неподдерживаемого адаптера явно ограничить функцию или использовать заранее согласованное сопоставление.
- <b>F08-R07.</b> Проверить сочетание с акциями/бонусами, отменой и возвратом. Не выводить поддержку комбо во всех внешних каналах из поддержки на собственной витрине.

<b>Критерии приёмки</b>

- [ ] <b>F08-A01.</b> Нельзя оформить набор без обязательной группы или с недопустимой комбинацией.
- [ ] <b>F08-A02.</b> Цена на витрине, в корзине, заказе и передаче во внешнюю систему совпадает по согласованным правилам.
- [ ] <b>F08-A03.</b> Кухня получает однозначный состав, включая половины и добавки.
- [ ] <b>F08-A04.</b> Стоп-лист компонента и повтор старого заказа корректно объясняются гостю.

<b>Где появится в продукте.</b> Каталог → Конструктор набора/половинок; карточка товара; корзина; карточка кухни.

<b>Зависимости.</b> Каталог, модификаторы, цены, стоп-листы и возможности адаптеров F06.

<b>Где посмотреть и что изучить</b>

- [STARTER для пиццерий](https://starterapp.ru/for-whom/pizza) — Посмотреть половинки, размеры, тесто и добавки.
- [ReStar](https://restarapp.com/) — Посмотреть заявленные конструкторы и половинки; детали формулы цены Delivest согласовать отдельно.

<b>9. F09 — Печать и устойчивость рабочего места при сбоях связи</b>

<b>Цель.</b> Дать персоналу понятное состояние печати и восстановление работы после сетевого сбоя; не терять действия и не заявлять неподтверждённый офлайн.

<b>Что уже есть / что проверить.</b> POS и кухня уже есть; облачная фискализация не равна локальной аппаратной печати. Аппаратная печать и полноценный офлайн ранее не обнаружены. Этот пункт требует особенно аккуратного разделения объёма.

<b>Основной сценарий.</b> Кухонное задание отправлено на принтер, связь прервалась. Сотрудник видит неопределённый результат и может выполнить контролируемую повторную печать, не создавая новый заказ.

<b>Функциональные требования</b>

- <b>F09-R01.</b> Разделить типы документов: кухонный талон, нефискальная информация и фискальный чек. Не выдавать обычную распечатку за фискальный чек.
- <b>F09-R02.</b> Сначала выбрать поддерживаемое оборудование/подключение и пилотный сценарий. Затем определить точку печати и шаблоны по филиалам/станциям.

## Согласованные продуктовые решения — обсуждение 7 ноября 2026

<b>Статус:</b> согласованная продуктовая концепция для следующей редакции ТЗ. Это не означает реализацию функций. Ранее утверждённый список F01–F10 сохраняется как историческая версия; решения ниже уточняют приоритеты и объём ближайшего этапа.

### Общий принцип UX

- Любую крупную функцию можно выключить, быстро включить с понятными настройками либо настроить глубоко и гибко.
- Сложные настройки оформляются последовательными мастерами с небольшим количеством понятных шагов, а не одной перегруженной формой. Этот принцип применять не только к маркетингу, но и к другим подходящим разделам продукта.
- Независимые модули должны быть повторно используемыми в разных функциях Delivest. Технические детали расписаний, очередей и оптимизации обсудить позже.

### Изменение ближайшего продуктового объёма

- <b>F01 — развиваем:</b> сегменты клиентов, постоянные маркетинговые политики, мотивации и уведомления.
- <b>F04 — развиваем:</b> аналитика воронки, особенно определение этапа, на котором покупатель прекращает оформление. Брошенная корзина не запускает автоматическую выдачу скидки в F01.
- <b>F02 — исключить из ближайшего этапа:</b> отзывы не нужны, поскольку усложняют минималистичный клиентский UX.
- <b>F05 — исключить из ближайшего этапа:</b> реферальная программа не нужна.
- Остальные направления F03, F06–F10 в этом обсуждении не пересматривались.

### Независимый модуль Segments

- Поддерживать <b>динамические</b> и <b>ручные</b> группы клиентов. Группы существуют независимо от маркетинговых политик и доступны другим модулям.
- Область действия выбирается при создании: вся сеть, один филиал или несколько филиалов. Активность и заказы оцениваются в выбранной области.
- Динамическая группа определяется только правилами: ручных включений и исключений в ней нет. Исключения отдельных клиентов и групп задаются в конкретной политике.
- Редактор условий: последовательный мастер, классические признаки — давность регистрации, количество и даты заказов, активность/неактивность, сумма покупок, средний чек, филиалы, предпочтения, бонусы/промо и другие доступные данные. Условия можно сочетать понятным образом. Для ручной группы сотрудники управляют участниками.
- Если изменение сегмента затрагивает действующие политики, показать список затронутых политик и запросить подтверждение применения. После подтверждения новые условия действуют на будущие запуски; сохранять историю изменений. Не применять изменение незаметно.

### F01 — постоянные маркетинговые политики

- Политики — самостоятельные постоянно действующие правила, а не одноразовые рассылки. Пользователь может создавать сколько угодно политик, без искусственного продуктового лимита.
- Каждая политика выбирает аудиторию через Segments, задаёт исключения, мотивацию, каналы уведомления и ограничения; периодически проверяет аудиторию и выдаёт подходящим клиентам мотивацию. Владелец описал это как ночные воркеры; точную техническую схему и расписание отложили.
- Основной сценарий: клиент ранее делал заказы, затем не заказывал заданное число дней. Клиенты, просто собравшие и бросившие корзину, не считаются неактивными для этого сценария.
- <b>Повторная выдача:</b> одна выдача на один период неактивности для каждой политики. Пока клиент не сделал новый заказ, эта же политика не выдаёт мотивацию повторно, даже после истечения промокода. Новый заказ начинает новый цикл; после следующего периода неактивности правило может сработать снова.
- Разные политики независимы и могут совпасть по аудитории; возможные исключения задаются в самих политиках.
- При первом включении ресторан выбирает: обработать всю уже подходящую аудиторию либо только будущих участников. До запуска показать охват и возможные затраты.
- Политики можно включать и выключать, просматривать результаты и историю. Настройка последовательная: аудитория → мотивация → оповещение → ограничения → проверка и включение.
- Для мотивации переиспользовать существующие Promo Engine (промокоды, акции, скидки, подарки и другие поддерживаемые варианты) и бонусный модуль; не создавать дублирующий движок наград.

### Самостоятельный модуль Notifications

- Каналы: SMS, Push и сообщения на клиентском сайте; модуль нужен не только маркетингу. Ресторан выбирает применимые каналы для политики.
- На клиентском сайте уведомления отображаются в <b>существующей области под хедером, там же, где активный заказ</b>. Активный заказ и уведомления показываются одновременно, отдельный центр уведомлений в клиентском UX не требуется.
- Уведомление остаётся до <b>ручного закрытия</b> клиентом; просмотр сам по себе его не скрывает. Закрытие действует <b>только на текущем устройстве</b>, на другом устройстве карточка может отображаться.
- Закрытие уведомления не отменяет промокод, бонусы или само предложение. Утратившее актуальность предложение не следует показывать как действующее.
- Разделить доставку уведомления и право клиента на мотивацию. Учитывать согласия и доступность маркетинговых каналов.

### Расширенная аналитика F01 и F04

- Для каждой политики — расширенный отчёт: аудитория и исключения, выдачи, отправки и доступные статусы доставки, переходы, вернувшиеся клиенты, заказы, выручка по связанным заказам, использование промокодов/бонусов, стоимость скидок и SMS, динамика и сравнение политик/периодов/филиалов.
- Не выдавать корреляцию за доказанный прирост продаж: заказы после кампании не обязательно вызваны кампанией. A/B-тесты и контрольные группы не входят в обязательный первый объём.
- F04 должна показывать, на каком этапе клиент отсеялся: посещение, каталог/товар, корзина, начало оформления, завершение заказа и другие фактически доступные этапы. Конкретную схему событий и интерфейс аналитики ещё предстоит согласовать.

<b>Принято владельцем:</b> аналитика всей франшизы должна быть доступна администратору платформы и владельцу франшизы. Сводные показатели включают заказы, выручку, средний чек, отмены, каналы продаж, источники, воронку, покупателей и сравнение ресторанов/филиалов. Доступ ограничивается областью полномочий; обычные владельцы ресторанов не видят чужие данные. Агрегация не должна удваивать заказы и выручку.

Не обещать, что ночной расчёт всегда возможен: при круглосуточной нагрузке нужен лимит ресурсов и адаптивное планирование. Интервалы для воронки, ссылок и удержания согласовать отдельно.

## Решение по оркестратору — 8 ноября 2026

<b>Утверждено владельцем:</b> адаптивный оркестратор отложенных задач учитывает текущую нагрузку системы и сроки обновления аналитики; выбирает подходящее время выполнения тяжёлых расчётов вместо жёсткого ночного запуска.

<b>Проектные предложения для дальнейшего согласования:</b> использовать общий механизм для некритичных фоновых задач разных модулей; отдельные Oban-очереди и лимиты конкурентности; мониторить состояние PostgreSQL, критических очередей, CPU и latency; предотвращать бесконечное откладывание, явно показывать устаревшие данные и нарушения сроков. Классы приоритетов и точные SLA пока не утверждены.

## F04 — сроки обновления аналитики, решение 8 ноября 2026

<b>Утверждено владельцем:</b> сбалансированная свежесть данных: заказы и выручка обновляются оперативно; воронка оформления, рекламные ссылки и источники — не позднее 15 минут; сложные расчёты (включая удержание, уникальных покупателей и тяжёлые сводки франшизы) — не позднее 24 часов. Это целевые сроки, не подтверждённая эксплуатационная гарантия.

<b>Проектные предложения, требующие согласования:</b> контроль CPU, PostgreSQL latency/queue и критических Oban-очередей; ограничение параллельности; приостановка новых тяжёлых заданий при пике; безопасные checkpoints для длительных расчётов; индикация времени последнего успешного расчёта и нарушения SLA. Не допускать конкуренции тяжёлой аналитики с критическими операциями заказа и оплаты.

## Оркестратор — права управления, решение 8 ноября 2026

<b>Утверждено владельцем:</b> автоматический оркестратор работает самостоятельно, но администратор платформы может управлять им. Владельцы франшиз и ресторанов получают аналитику, но не права управления общими серверными ресурсами.

<b>Предлагаемый интерфейс и меры безопасности (ещё не утверждены по деталям):</b> Системное администрирование → Фоновые задачи; просмотр очередей, ошибок и сроков; ручной пересчёт, безопасный повтор и приостановка некритичных задач; аудит ручных действий; отдельная защита критических очередей заказов и платежей; безопасное восстановление после перезапуска, справедливое распределение вычислений между франшизами, индикация устаревших данных.

## Оркестратор — справедливое распределение, решение 8 ноября 2026

<b>Утверждено владельцем:</b> справедливо распределять ресурсы тяжёлых фоновых расчётов между франшизами и самостоятельными ресторанами. Крупная сеть не должна блокировать небольшие заведения; неиспользуемые ресурсы могут временно перераспределяться другим задачам.

<b>Предложение для реализации (детали ещё не утверждены):</b> tenant-aware weighted fair scheduling с ограничением параллельности на организацию, общим лимитом аналитических заданий, приоритетом критических очередей и учётом deadline. Не создавать физическую Oban-очередь на каждую франшизу без измеренной необходимости. Проверить справедливость и отсутствие starvation под нагрузкой.

## Оркестратор — восстановление после сбоев, решение 8 ноября 2026

<b>Утверждено владельцем:</b> при сбое или перезапуске незавершённый аналитический расчёт запускается заново с начала, без возобновления с checkpoint. Это правило относится к аналитическим расчётам, а не автоматически ко всем внешним side-effect jobs (платежи, уведомления и интеграции).

<b>Проектные защитные требования:</b> повтор идемпотентен, результаты публикуются атомарно только после полного успеха; до этого доступна последняя завершённая версия. Ограничивать попытки, использовать backoff и учитывать текущую нагрузку. Не допускать параллельных конфликтующих пересчётов одного набора данных. При многократных сбоях показывать ошибку администратору. Размер и длительность одного расчёта требуют отдельного ограничения.

## Оркестратор — накопившиеся задания, решение 8 ноября 2026

<b>Утверждено владельцем:</b> после простоя объединять дублирующие и устаревшие аналитические пересчёты, сохраняя все необходимые исторические данные. Не выполнять каждое накопленное задание, если его результат полностью покрывается актуальным расчётом.

<b>Проектные ограничения:</b> дедупликация по области данных (франшиза/ресторан/филиал), виду отчёта, периоду и параметрам; защита от параллельных конфликтующих вычислений; аудит замены заданий; постепенное восстановление нагрузки. Это не правило для платежей, заказов или внешних side-effect jobs. Точный алгоритм coalescing требует проектирования и тестов.

## Оркестратор — отображение проблем, решение 8 ноября 2026

<b>Утверждено владельцем:</b> проблемы оркестратора показываются только в панели администратора платформы. Не создавать отдельные push, email, Telegram и другие активные уведомления об ошибках фоновой аналитики.

<b>Предлагаемые детали интерфейса:</b> раздел «Системное администрирование → Фоновые задачи» показывает ошибки, задержки, состояние очередей, количество попыток, причины, последний успешный расчёт и разрешённые действия. Пользователям аналитики показывать время последнего успешного обновления данных. Автоматические retries и recovery остаются активными; отсутствие уведомлений не означает подавление ошибок в журналах и мониторинге.

## F04 — хранение агрегатов, решение 8 ноября 2026

<b>Утверждено владельцем:</b> основные аналитические отчёты читают заранее рассчитанные и сохранённые агрегаты, а не выполняют тяжёлые пересчёты при каждом открытии страницы. Оркестратор готовит и обновляет их с ранее согласованной свежестью (продажи оперативно, воронка/ссылки до 15 минут, сложная аналитика до 24 часов).

<b>Проектные требования:</b> агрегаты по периодам, каналам, ресторанам/филиалам и франшизам; атомарная публикация полной версии; повторный пересчёт без удвоения; изоляция доступа; возможность полного исторического пересчёта при исправлении ошибок; время последнего успешного обновления. Предлагается начать с PostgreSQL без нового аналитического хранилища до появления измеренной необходимости.

## F04 — срок хранения агрегатов, решение 8 ноября 2026

<b>Утверждено владельцем:</b> готовые аналитические агрегаты хранятся 3 года (36 месяцев), затем удаляются по политике хранения. Это не распространяется автоматически на исходные заказы, платежи и финансовые документы. Срок хранения детальных событий воронки и посещений остаётся открытым.

<b>Предлагаемая реализация:</b> плановая очистка устаревших агрегатов оркестратором с ограничением нагрузки и аудитом результата; определить границу по календарным датам и часовым поясам при техническом проектировании. Предварительная оценка для 5 филиалов и условных 20 КБ агрегатов на филиал в день — около 107 МБ за 3 года, без сырых событий, индексов вне допущения, backup и временных данных; реальный объём требует замера.

## Управление доступностью функций и экономия ресурсов — решение 8 ноября 2026

<b>Утверждено владельцем:</b> необязательные функции (включая F01 группы клиентов и маркетинговые политики, F04 расширенную аналитику, рекламные ссылки, аналитику франшизы и связанные фоновые расчёты) должны работать только при наличии доступа у соответствующей франшизы/ресторана и при включении функции в админке. Цель — не расходовать вычислительные ресурсы на небольшие кафе, которым эти возможности не нужны. Недостаточно скрыть интерфейс: выключенная функция не должна запускать свои воркеры, агрегирование и необязательный сбор событий.

<b>Проектные инварианты:</b> проверять право и активацию на сервере при API-запросе, сборе необязательного события, планировании и исполнении jobs; существующие заказы, платежи и необходимые интеграции не зависят от отключения аналитики. При отключении новые задачи не ставятся, ожидающие задания безопасно пропускаются, работающие проверяют возможность остановки без нарушения целостности; сохранить аудит смены настроек. Разделить права платформы на предоставление функции и включение внутри организации. Уровень наследования франшиза → ресторан → филиал и поведение накопленных результатов при повторном включении требуют отдельного согласования.

<b>Предлагаемая реализация:</b> единый реестр feature flags/entitlements с tenant-scoped настройками и явными зависимостями между функциями; общие дешёвые бизнес-события не отключать, если они необходимы заказам или другим включённым модулям. Избегать создания тяжёлых worker jobs для неактивных tenants.

## Feature Management — иерархия, решение 8 ноября 2026

<b>Утверждено владельцем:</b> управление необязательными функциями иерархическое: франшиза → ресторан → филиал. Нижестоящий уровень не может самостоятельно активировать функцию, если она недоступна или запрещена на вышестоящем. Для самостоятельных ресторанов нужен эквивалентный корневой контекст доступа без обязательной франшизы.

<b>Предлагаемые правила:</b> entitlement платформы и настройка активации организации учитываются совместно; на каждом уровне можно ограничить область работы функции. Выключение должно блокировать API, сбор необязательных событий, постановку и исполнение соответствующих аналитических jobs, но не критические бизнес-процессы. При смене состояния учитывать зависимости, аудит и срок хранения старых результатов. Модель наследования (явные on/off/inherit), кто именно управляет каждым уровнем, и политика повторного включения требуют дальнейшего согласования.

## Feature Management — состояние новых организаций, решение 8 ноября 2026

<b>Утверждено владельцем:</b> для новых ресторанов и филиалов все дополнительные необязательные функции выключены по умолчанию, даже если разрешены франшизе. Включение требует явного действия в админке на соответствующем уровне и соблюдения иерархии франшиза → ресторан → филиал. Базовые процессы заказов, оплаты, кухни и необходимые интеграции не отключаются этой политикой.

<b>Предлагаемые детали интерфейса:</b> различать доступность, включение, выключение и блокировку вышестоящим уровнем; показывать зависимости функций и предупреждать о последствиях включения/отключения. Для существующих организаций при миграции нужна отдельная безопасная политика, не следует автоматически менять действующие настройки.

## Feature Management — повторное включение, решение 8 ноября 2026

<b>Утверждено владельцем:</b> после повторного включения необязательной функции сбор новых событий и расчётов начинается с момента включения; пропущенный период не восстанавливается автоматически. Ранее успешно рассчитанные агрегаты остаются доступными в пределах срока хранения. Период отключения обозначается как «данные не собирались», не как нулевые показатели.

<b>Инварианты:</b> отключение аналитики не удаляет и не останавливает базовые заказы и платежи; повторное включение не запускает тяжёлый исторический backfill. Не смешивать отсутствие данных с нулевыми значениями при построении сравнений.

## Feature Management — гранулярность переключателей, решение 8 ноября 2026

<b>Утверждено владельцем:</b> отдельные переключатели для крупных функциональных блоков, а не один общий на F01/F04 и не переключатель на каждую метрику. Выделить: группы клиентов (F01), маркетинговые политики (F01), воронку заказов (F04), рекламные ссылки и их отслеживание (F04), расширенную аналитику каналов/покупателей/сравнения (F04), сводную аналитику франшизы (F04). Каждый блок должен включаться только при доступности в иерархии и явной активации.

<b>Проектное уточнение:</b> у каждого блока отдельные серверные guards, сбор необязательных событий и планирование jobs; общие необходимые зависимости могут использоваться несколькими активными блоками без дублирования. Точную матрицу зависимостей и поведение при отключении родительской функции согласовать отдельно.

## Feature Management — отключение с зависимостями, решение 8 ноября 2026

<b>Утверждено владельцем:</b> при отключении функционального блока, от которого зависят другие активные возможности, Delivest показывает предупреждение с перечнем затрагиваемых функций и процессов и требует явного подтверждения. После подтверждения зависимые процессы безопасно приостанавливаются; история и настройки не удаляются.

<b>Проектные требования:</b> серверная проверка зависимостей и полномочий; учёт каскада франшиза → ресторан → филиал; журнал аудита подтверждения; безопасная остановка необязательных jobs; информативный статус причины приостановки. При повторном включении не отправлять автоматически пропущенные маркетинговые сообщения. Не затрагивать критические заказы и платежи.

## Feature Management — полномочия, решение 8 ноября 2026

<b>Утверждено владельцем:</b> предоставление доступа, включение и отключение всех дополнительных функций на уровне франшизы, ресторана и филиала выполняет <b>только администратор платформы Delivest</b>. Владельцы франшиз, владельцы ресторанов и сотрудники не могут менять состояние этих feature flags. Они могут использовать доступные функции в рамках обычных прав и видеть их статус при необходимости.

<b>Уточнение предыдущих решений:</b> прежняя формулировка «включение в админке ресторана/франшизы» означает централизованное включение администратором платформы для соответствующей области, а не право владельца самостоятельно активировать функцию. Иерархия и отключённое состояние по умолчанию сохраняются.

<b>Проектные требования:</b> серверная авторизация для каждой операции управления флагами; аудит кто/когда/где/что изменил; проверка зависимостей и подтверждение перед отключением; отсутствие автоматического backfill при повторном включении.

## Feature Management — видимость выключенных функций, решение 8 ноября 2026

<b>Утверждено владельцем:</b> в админке ресторана/франшизы отключённые дополнительные функции полностью скрываются: нет пунктов меню, вкладок, кнопок, настроек и рекламного каталога выключенных возможностей. Видны только включённые в соответствующей области функции, на которые у пользователя есть права. Администратор платформы сохраняет полный интерфейс управления всеми флагами.

<b>Инварианты:</b> скрытие UI не заменяет серверный запрет API и остановку необязательных событий/jobs; при отключении одного блока F04 остальные активные блоки продолжают работать. Сохранённые данные подчиняются ранее утверждённой политике хранения.

## Feature Management — массовое управление, решение 8 ноября 2026

<b>Утверждено владельцем:</b> администратор платформы может управлять дополнительными функциями индивидуально и массово для выбранных франшиз, ресторанов и филиалов. Шаблоны наборов функций не утверждены и не входят в текущее решение.

<b>Проектные требования:</b> массовое включение/отключение с предварительным просмотром списка объектов, проверкой прав и иерархических ограничений, анализом зависимостей и явным подтверждением; результат по каждому объекту (успех, пропуск, ошибка) и аудит. Избегать неочевидного частичного применения: правила частичного успеха/атомарности согласовать отдельно.

## Feature Management — частичный успех массовых операций, решение 8 ноября 2026

<b>Утверждено владельцем:</b> массовое включение/отключение функций допускает частичный успех. Для разрешённых организаций изменения применяются; организации с запретом, конфликтом зависимостей или ошибкой пропускаются с конкретной причиной. Ошибка одного объекта не откатывает успешные изменения других.

<b>Проектные требования:</b> предварительный просмотр ожидаемого результата; независимая транзакционная обработка каждого объекта с повторной серверной проверкой на момент применения; отчёт по статусам «успешно / пропущено / ошибка»; аудит по каждому объекту; безопасный идемпотентный повтор без дублирования побочных эффектов. Отчёт предварительного просмотра может измениться при конкурентных обновлениях — итоговая серверная проверка обязательна.

## Feature Management — миграция существующих организаций, решение 8 ноября 2026

<b>Утверждено владельцем:</b> при внедрении Feature Management существующим ресторанам сохранять уже используемые функции; новые дополнительные функции включаются исключительно администратором платформы. Для новых ресторанов/филиалов дополнительные функции выключены по умолчанию.

<b>Проектные требования:</b> аудит реально используемых функций до миграции; сохранение эффективных прав и состояния на уровне франшизы/ресторана/филиала; проверка зависимостей; безопасный rollout серверных guards и worker gating без остановки базовых заказов/платежей; проверка результата и возможность отката конфигурации. Неопределённое текущее использование не трактовать автоматически как разрешение или запрет: требуются проверка и явное решение.

## Feature Management — журнал изменений, решение 8 ноября 2026

<b>Утверждено владельцем:</b> базовый журнал изменений дополнительных функций, без отдельной системы версий конфигураций или автоматического отката. Записывать администратора платформы, время, идентификатор функции, действие включить/отключить и область (франшиза/ресторан/филиал).

<b>Связь с массовыми операциями:</b> сохранять записи по фактически изменённым объектам; отдельный результат массового действия должен по-прежнему показывать успешные, пропущенные и ошибочные объекты, как ранее утверждено. Технические ошибки остаются в системных логах; базовый журнал не должен подменять диагностику.

## Feature Management — применение изменений, решение 8 ноября 2026

<b>Утверждено владельцем:</b> после сохранения изменения feature flag немедленно вступают в силу на сервере, без перезапуска Phoenix/Oban; в уже открытом интерфейсе изменение отображается после обновления страницы. Real-time синхронизация открытых вкладок не требуется.

<b>Инварианты:</b> сервер проверяет эффективное состояние функции на каждом защищённом действии; фоновые задания проверяют флаг перед исполнением; отключение не оставляет частично опубликованные агрегаты. Не полагаться на старое состояние UI или устаревший cache прав. Применение для работающих задач должно быть безопасным и соответствовать ранее согласованным зависимостям.

## Feature Management — автоматическая активация зависимостей, решение 8 ноября 2026

<b>Утверждено владельцем:</b> при включении дополнительной функции Delivest автоматически включает её обязательные функциональные зависимости, без отдельного ручного включения. Действие инициирует только администратор платформы.

<b>Инварианты:</b> проверять entitlement и ограничения иерархии франшиза → ресторан → филиал; не обходить запреты верхних уровней. Если обязательная зависимость недоступна, не активировать основную функцию и показать причину. В рамках одного объекта основную функцию и необходимые зависимости включать атомарно. В базовом журнале фиксировать каждую изменённую функцию. Автоматическая активация не запускает маркетинговые кампании и не создаёт исторический backfill; необязательные события собираются только с момента включения. При массовом управлении сохраняется ранее выбранный частичный успех между организациями.

<b>Требует уточнения:</b> как вести себя при последующем отключении основной функции, если её автоматически включённые зависимости используются и другими активными функциями.
