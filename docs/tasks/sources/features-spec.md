<a id="f01"></a>
**1. F01 — Сегменты клиентов и кампании возврата**

**Цель.** Дать заведению управляемый инструмент возвращения гостей и возможность оценивать результат действий.

**Что уже есть / что проверить.** Есть клиентские карточки, история заказов, бонусы, промо и Web Push. Сегменты, адресные кампании и полный цикл их измерения ранее не обнаружены. Существующее напоминание об истечении бонусов нужно переиспользовать, не дублировать.

**Основной сценарий.** Маркетолог выбирает «не заказывали более заданного числа дней», видит размер аудитории, создаёт предложение, проверяет сообщение, запускает кампанию и затем видит результаты.

**Функциональные требования**

<a id="f01-r01"></a>
- **F01-R01.** Сегменты: новые гости, первый завершённый заказ, давно не заказывали, постоянные гости. Пороги дней, числа заказов и периода настраиваются; определения показываются пользователю. Доступ ограничен сетью и разрешёнными филиалами.
<a id="f01-r02"></a>
- **F01-R02.** Редактор кампании: название, аудитория, сообщение, ссылка на витрину/предложение, канал из доступных, предварительный просмотр, тестовая отправка сотруднику, время запуска в заданном часовом поясе.
<a id="f01-r03"></a>
- **F01-R03.** Перед запуском показывать доступную аудиторию и исключения: нет разрешения на канал, нет доступного адресата, частотный лимит, исключённый клиент. Повторно проверять допустимость отправки непосредственно перед доставкой.
<a id="f01-r04"></a>
- **F01-R04.** Статусы: черновик, запланирована, выполняется, приостановлена/отменена, завершена. Повтор фоновой задачи не должен повторно отправлять одно и то же сообщение адресату.
<a id="f01-r05"></a>
- **F01-R05.** Второй шаг: автоматические сценарии после первого заказа и периода неактивности. Выход из сценария после нового заказа; частотные ограничения между кампаниями. Триггеры истечения бонусов согласовать с существующим механизмом.
<a id="f01-r06"></a>
- **F01-R06.** Отчёт: выбранные/исключённые адресаты, отправки, подтверждённая доставка только при наличии сигнала провайдера, переходы, связанные заказы, выручка и затраты бонусов. Окно атрибуции показывать явно; наблюдаемая выручка не равна доказанному приросту.
<a id="f01-r07"></a>
- **F01-R07.** Использовать существующий движок скидок/бонусов. Многоканальные цепочки, произвольный визуальный конструктор и полный RFM можно отложить. Контрольную группу предусмотреть как следующий этап оценки эффекта.

**Критерии приёмки**

<a id="f01-a01"></a>
- [ ] **F01-A01.** На подготовленной базе сегменты выбирают ожидаемых гостей; отменённые заказы учитываются согласно явно заданной политике.
<a id="f01-a02"></a>
- [ ] **F01-A02.** Гость без разрешения на выбранный канал исключается; повтор запуска и повтор доставки задачи не создают дублей сообщений.
<a id="f01-a03"></a>
- [ ] **F01-A03.** После нового заказа клиент не получает устаревшее предложение «вернуться», если сценарий предусматривает выход.
<a id="f01-a04"></a>
- [ ] **F01-A04.** Отчёт объясняет значения и окно атрибуции; отказ канала виден оператору, недоступные метрики не выдумываются.

**Где появится в продукте.** Клиенты → Сегменты; Маркетинг → Кампании; карточка кампании → результаты.

**Зависимости.** F04 — модель событий и атрибуция; существующие бонусы, промо и уведомления.

**Где посмотреть и что изучить**

- [STARTER: ресторанное решение](https://starterapp.ru/solutions/restaurant) — Изучить RFM, сегменты и триггерные рассылки. Это описание поставщика, не спецификация его внутренней реализации.
- [eDA: уведомления](https://eda-platform.ru/functional/notifications) — Посмотреть аудитории и каналы клиентских уведомлений.

<a id="f02"></a>
**2. F02 — Отзывы после заказа и обработка проблем**

**Цель.** Замкнуть цикл «заказ → обратная связь → реакция сотрудника → решение», замечать повторяющиеся проблемы филиалов.

**Что уже есть / что проверить.** Есть входящая обратная связь Яндекс Еды. Собственный сбор оценки после заказа и единая очередь решения проблем ранее не обнаружены. Автозагрузка публичного рейтинга Яндекса — отдельная незавершённая функция, её не смешивать с этим модулем.

**Основной сценарий.** После завершения заказа гость получает приглашение оценить опыт. При проблеме сотрудник видит связанный заказ, назначает ответственного и фиксирует решение.

**Функциональные требования**

<a id="f02-r01"></a>
- **F02-R01.** Настройки запроса оценки по филиалу: включение, задержка после завершения заказа, канал и частотный лимит. Не отправлять запросы по отменённым заказам.
<a id="f02-r02"></a>
- **F02-R02.** Короткая форма: общая оценка, комментарий и категории проблемы — еда, доставка, комплектация, другое. Детальные оценки категорий допустимы как последующее расширение.
<a id="f02-r03"></a>
- **F02-R03.** Одна обратная связь на заказ с согласованным правилом редактирования. Ссылка не раскрывает чужие заказы, контакты или платёжные данные; срок действия и доступ гостя определить при проектировании.
<a id="f02-r04"></a>
- **F02-R04.** Очередь обращений: фильтры филиала, периода, оценки, категории, ответственного и статуса. Статусы: новое, в работе, решено. Порог проблемной оценки настраивается.
<a id="f02-r05"></a>
- **F02-R05.** Карточка связывает отзыв, заказ и клиента с учётом прав. Сотрудник фиксирует внутреннюю заметку, связь с гостем и результат. Компенсации только отдельным разрешённым действием через существующие механизмы.
<a id="f02-r06"></a>
- **F02-R06.** Показывать время реакции, долю ответивших и повторяющиеся причины проблем. Не публиковать внутренние комментарии сотрудников.
<a id="f02-r07"></a>
- **F02-R07.** Публичная лента отзывов и внешние площадки не входят в первый выпуск. Если позже появится внешнее приглашение, не фильтровать его только по положительным оценкам.

**Критерии приёмки**

<a id="f02-a01"></a>
- [ ] **F02-A01.** Завершённый заказ получает один запрос; повторное событие завершения не дублирует отправку.
<a id="f02-a02"></a>
- [ ] **F02-A02.** Низкая оценка создаёт видимое обращение с правильным заказом и филиалом.
<a id="f02-a03"></a>
- [ ] **F02-A03.** Недоступный канал не ломает заказ; проблема отправки диагностируется.
<a id="f02-a04"></a>
- [ ] **F02-A04.** Изменение ответственного и статуса сохраняется в истории; сотрудник без прав не видит чужую область данных.

**Где появится в продукте.** Страница оценки гостя; Заказы → Обратная связь; карточка обращения; настройки филиала.

**Зависимости.** События завершения заказа, уведомления, роли и права; F01 для общих частотных ограничений.

**Где посмотреть и что изучить**

- [STARTER: ресторанное решение](https://starterapp.ru/solutions/restaurant) — Посмотреть заявленные отзывы после заказа и работу с обратной связью.
- [Foodeon: доставка](https://foodeon.com/ru/delivery) — Посмотреть сценарий обратной связи руководству; не считать маркетинговую страницу доказательством конкретного workflow.

<a id="f03"></a>
**3. F03 — Вместимость слотов и управление загрузкой**

**Цель.** Не обещать гостю время, которое заведение не сможет выдержать, и предлагать ближайшую доступную альтернативу.

**Что уже есть / что проверить.** Предзаказ, расписание, специальные часы, паузы и выбор времени уже есть. В ранее просмотренной логике не найдены квоты нагрузки по временному интервалу.

**Основной сценарий.** У филиала заполнен интервал самовывоза. Гость видит его недоступность и выбирает следующий; отмена заказа освобождает зарезервированную нагрузку по согласованным правилам.

**Функциональные требования**

<a id="f03-r01"></a>
- **F03-R01.** Настраиваемые интервалы и лимиты по филиалу, дню и способу получения. Для первого выпуска считать заказы; расчёт по трудоёмкости блюд — отдельное расширение.
<a id="f03-r02"></a>
- **F03-R02.** Разделять время готовности и время получения/доставки. Явно определить, к какому времени относится квота и как учитываются ASAP-заказы.
<a id="f03-r03"></a>
- **F03-R03.** При заполнении предлагать следующий доступный интервал. Соблюдать существующие рабочие и специальные часы, часовой пояс филиала и ручную паузу.
<a id="f03-r04"></a>
- **F03-R04.** Согласовать момент резервирования и срок удержания места при ожидании онлайн-оплаты. Отмена, истечение резерва и поздний платёж обрабатываются без отрицательной или бесконтрольной вместимости.
<a id="f03-r05"></a>
- **F03-R05.** Проверять доступность при финальном подтверждении заказа, а не только в интерфейсе. Одновременные покупатели не могут занять одно последнее место.
<a id="f03-r06"></a>
- **F03-R06.** Оператор видит загрузку и может изменить лимит или сделать разрешённое исключение с причиной. Уже принятые заказы при уменьшении лимита не теряются.
<a id="f03-r07"></a>
- **F03-R07.** Определить учёт заказов из POS, админки и внешних каналов: должны влиять на реальную нагрузку, но отклонять внешние заказы можно только в рамках контракта канала. Политику подтвердить на следующем этапе.

**Критерии приёмки**

<a id="f03-a01"></a>
- [ ] **F03-A01.** При одновременной попытке занять последнее место квота не превышается.
<a id="f03-a02"></a>
- [ ] **F03-A02.** Отмена/истечение освобождает резерв ровно один раз; повторные события безопасны.
<a id="f03-a03"></a>
- [ ] **F03-A03.** Проверены полночь, особые часы, пауза, смена дня в часовом поясе филиала.
<a id="f03-a04"></a>
- [ ] **F03-A04.** Гость получает объяснение и альтернативу; изменение лимитов не удаляет принятые заказы.

**Где появится в продукте.** Настройки филиала → Загрузка и слоты; выбор времени заказа; экран загрузки оператора.

**Зависимости.** Расписание, жизненный цикл заказа и оплаты; F07 для последующей связи с курьерскими ресурсами.

**Где посмотреть и что изучить**

- [STARTER: подготовка к праздникам](https://starterapp.ru/journal/get-ready-for-the-holidays) — Изучить интервалы, предзаказы и настройки приготовления. Источник не доказывает наличие полного механизма квот.
- [Смартомато: автораспределение](https://help.smartomato.ru/hc/user-guide/articles/auto-dispatch) — Изучить будущие заказы и отложенный запуск диспетчеризации.

<a id="f04"></a>
**4. F04 — Воронка заказов и источники привлечения**

**Цель.** Показать заведению, откуда приходят заказы и на каком этапе гости прекращают оформление.

**Что уже есть / что проверить.** Продажи и операционная отчётность есть. Связка источника посещения с шагами оформления и итогом заказа ранее не обнаружена.

**Основной сценарий.** Владелец сравнивает источники трафика и видит, что после расчёта доставки часть гостей покидает оформление; проверяет эффект изменения условий.

**Функциональные требования**

<a id="f04-r01"></a>
- **F04-R01.** Словарь событий: просмотр меню, просмотр товара при необходимости, добавление в корзину, начало оформления, выбор получения, создание заказа, подтверждённая оплата, отмена и завершение.
<a id="f04-r02"></a>
- **F04-R02.** Сохранять UTM и источник в рамках согласованной модели атрибуции. Показать различия прямых визитов, неизвестного источника и недоступных данных.
<a id="f04-r03"></a>
- **F04-R03.** Разделять созданные, оплаченные и выполненные заказы. Для наличных/офлайн-оплаты не применять платёжный шаг так, будто онлайн-оплата обязательна.
<a id="f04-r04"></a>
- **F04-R04.** Дедупликация событий и устойчивость к повторным вебхукам/перезагрузке страницы. Подтверждение оплаты брать из достоверного серверного состояния.
<a id="f04-r05"></a>
- **F04-R05.** Отчёт по периоду, филиалу, устройству при доступности данных и источнику: посетители/сессии согласно выбранному определению, переходы по шагам, конверсия и заказы.
<a id="f04-r06"></a>
- **F04-R06.** Интеграция с выбранной внешней аналитикой через явные события. Не строить собственный универсальный аналог систем веб-аналитики.
<a id="f04-r07"></a>
- **F04-R07.** Не передавать контакты, адрес доставки и другие лишние персональные данные в аналитические события. Согласовать разрешения, срок хранения и окно атрибуции.
<a id="f04-r08"></a>
- **F04-R08.** Связать кампании F01 и приглашения F05 с событиями без двойного суммирования выручки.

**Критерии приёмки**

<a id="f04-a01"></a>
- [ ] **F04-A01.** Тестовый путь от UTM до заказа сохраняет источник; обновление страницы не удваивает покупку.
<a id="f04-a02"></a>
- [ ] **F04-A02.** Отказ онлайн-оплаты не учитывается как оплаченный заказ; наличный заказ корректно отображается в своей воронке.
<a id="f04-a03"></a>
- [ ] **F04-A03.** Отчёт позволяет объяснить расхождения между сессиями, заказами и платежами.
<a id="f04-a04"></a>
- [ ] **F04-A04.** При блокировке внешней аналитики оформление продолжает работать.

**Где появится в продукте.** Аналитика → Воронка; Источники; настройки внешних аналитических систем.

**Зависимости.** Основа измерения F01/F05; существующие отчёты и события заказов.

<a id="f05"></a>
**5. F05 — Реферальная программа**

**Цель.** Дать гостям понятный способ приглашать друзей и измерять новые заказы от рекомендаций.

**Что уже есть / что проверить.** Бонусный учёт уже есть. Связка приглашения, первого выполненного заказа и награждения участников ранее не обнаружена.

**Основной сценарий.** Гость делится ссылкой, новый клиент оформляет первый заказ; после выполнения заказа начисляется предусмотренное правилами вознаграждение.

**Функциональные требования**

<a id="f05-r01"></a>
- **F05-R01.** Персональный код/ссылка, экран «пригласить друга», описание условий и история доступных пользователю наград.
<a id="f05-r02"></a>
- **F05-R02.** Настройки области действия программы: сеть/филиалы, порог заказа, вознаграждение сторонам, срок акции, лимиты приглашений и совместимость с другими предложениями.
<a id="f05-r03"></a>
- **F05-R03.** Однозначное правило нового клиента и закрепления пригласившего. Участие проверять серверно; спор нескольких кодов разрешать согласно показанному правилу.
<a id="f05-r04"></a>
- **F05-R04.** Начисление по подтверждённому событию выполнения и выбранному условию оплаты. Отмена/возврат обрабатываются обратной проводкой по согласованной политике, не удалением истории.
<a id="f05-r05"></a>
- **F05-R05.** Не допускать самоприглашения и повторного вознаграждения за один первый заказ. Предусмотреть лимиты и очередь подозрительных операций без автоматических наказаний по единственному слабому признаку.
<a id="f05-r06"></a>
- **F05-R06.** Отчёт: приглашения, новые клиенты, первые выполненные заказы, сумма наград, отмены наград. Применять существующий журнал бонусов.
<a id="f05-r07"></a>
- **F05-R07.** Зафиксировать нерешённую политику частичного возврата и случая, когда бонус уже потрачен.

**Критерии приёмки**

<a id="f05-a01"></a>
- [ ] **F05-A01.** Два одинаковых события выполнения дают одну награду.
<a id="f05-a02"></a>
- [ ] **F05-A02.** Существующий клиент не получает награду нового по установленным правилам; самоприглашение отклоняется.
<a id="f05-a03"></a>
- [ ] **F05-A03.** Отмена до выполнения не начисляет награду; возврат выполняет согласованную коррекцию.
<a id="f05-a04"></a>
- [ ] **F05-A04.** Клиент и оператор видят причину начисления/отказа, а аудит связывает награду с приглашением и заказом.

**Где появится в продукте.** Личный кабинет → Пригласить друга; Маркетинг → Реферальная программа; отчёт и журнал наград.

**Зависимости.** Бонусы, идентификация клиента, промо; F04 для измерения.

**Где посмотреть и что изучить**

- [STARTER: решение для пиццерий](https://starterapp.ru/for-whom/pizza) — Изучить заявленную реферальную программу и её место в маркетинге.
- [FoodSoul: настройки бонусов](https://wiki.foodsoul.ru/ru/public/info/settings/bonuses_settings) — Посмотреть описанные бонусные/реферальные настройки; конкретные правила Delivest сформулированы в этом ТЗ отдельно.

<a id="f06"></a>
**6. F06 — Подключение заведения и диагностика интеграций**

**Цель.** Довести подключение до проверенного первого заказа и сократить число проблем, для решения которых нужен разработчик.

**Что уже есть / что проверить.** Есть импорт меню, настройки филиалов, адаптеры ресторанных систем, журналы и диагностика. Требуется сначала сопоставить существующие экраны с целевым сценарием, затем закрыть пробелы; не создавать второй независимый центр диагностики.

**Основной сценарий.** Ответственный проходит настройки, видит непроверенные этапы, проводит контролируемый проверочный заказ и получает подтверждение, что статусы и оплата работают.

**Функциональные требования**

<a id="f06-r01"></a>
- **F06-R01.** Пошаговый маршрут: заведение и филиал; витрина; меню и сопоставления; зоны/график; способы оплаты; ресторанная система; уведомления; чек при применимости.
<a id="f06-r02"></a>
- **F06-R02.** У каждого шага разделять «настроено», «проверено», «ошибка», «не применимо». Наличие ключа не означает исправную интеграцию.
<a id="f06-r03"></a>
- **F06-R03.** Проверочный сценарий заказа с явным выбором тестовой/боевой среды. Не создавать реальные платежи или фискальные операции скрытно.
<a id="f06-r04"></a>
- **F06-R04.** Показывать возможности выбранного адаптера: что поддерживается для отправки, правок, отмены, меню и статусов; объяснять ограничения до выполнения действия.
<a id="f06-r05"></a>
- **F06-R05.** Единый список затронутых заказов и проблем: провайдер, филиал, время, последнее успешное действие, состояние, разрешённый следующий шаг. Переиспользовать имеющиеся health и журналы.
<a id="f06-r06"></a>
- **F06-R06.** Для неизвестного исхода отправки: сверка с внешней системой, привязка найденного внешнего заказа, разрешённая повторная отправка только после проверки отсутствия дубля. Сохранять автора и результат решения.
<a id="f06-r07"></a>
- **F06-R07.** Автоматические повторы только для безопасных случаев; недоступность внешней системы не должна выглядеть как успешное подтверждение.
<a id="f06-r08"></a>
- **F06-R08.** Передавать заведению итоговый список проверенных сценариев и оставшихся ограничений. Данные доступа в отчёты не включать.

**Критерии приёмки**

<a id="f06-a01"></a>
- [ ] **F06-A01.** Неисправная интеграция не получает статус «проверено» только из-за заполненных настроек.
<a id="f06-a02"></a>
- [ ] **F06-A02.** Тайм-аут с неизвестным исходом виден оператору и разрешается без неконтролируемого повторного создания заказа.
<a id="f06-a03"></a>
- [ ] **F06-A03.** Для неподдерживаемой операции пользователь видит понятное ограничение.
<a id="f06-a04"></a>
- [ ] **F06-A04.** Повторное открытие мастера сохраняет прогресс; изменение критичных настроек помечает зависимую проверку устаревшей.

**Где появится в продукте.** Подключение заведения; Настройки интеграций; Проблемы заказов; карточка проблемного заказа.

**Зависимости.** Существующие адаптеры и журналы. Это также часть предстартовой проверки всех новых функций.

**Где посмотреть и что изучить**

- [Delivest](https://app.notion.com/p/3e931ec95e44805fb97ac7d80efe6664) — Разделы «Интеграции» и «Маршрутизация заказов»: исходное описание текущего поведения.
- [Смартомато: интеграция Frontpad](https://help.smartomato.ru/hc/user-guide/articles/int-pos-frontpad) — Посмотреть пользовательское объяснение настройки интеграции. Мастер и состояния готовности здесь — предложение для Delivest, а не установленная копия интерфейса конкурента.

<a id="f07"></a>
**7. F07 — Автоназначение курьеров, объединение заказов и маршруты**

**Цель.** Сократить ручную диспетчеризацию и улучшить предсказуемость исполнения заказов при собственной доставке.

**Что уже есть / что проверить.** Есть собственные курьеры, назначения, геопозиция и диспетчерская. Оптимизация маршрутов ранее не найдена; полноту существующего назначения уточнить на следующем этапе.

**Основной сценарий.** Диспетчер видит рекомендованного курьера с объяснением; затем включает автоматический режим для подходящих заказов и при необходимости вмешивается.

**Функциональные требования**

<a id="f07-r01"></a>
- **F07-R01.** Этап 1 — рекомендация кандидатов по доступности, загрузке, смене, транспорту и времени до точки при наличии достоверных данных.
<a id="f07-r02"></a>
- **F07-R02.** Этап 2 — автоназначение с возможностью ручного изменения, фиксируемой причиной решения и защитой от назначения одного заказа двум курьерам.
<a id="f07-r03"></a>
- **F07-R03.** Учитывать будущие заказы и предполагаемую готовность; не вызывать курьера слишком рано без объяснимой политики.
<a id="f07-r04"></a>
- **F07-R04.** Батчинг: объединять только совместимые доставки с ограничениями по числу заказов, времени и обещанным срокам. Показать последовательность остановок и влияние добавления заказа.
<a id="f07-r05"></a>
- **F07-R05.** ETA и предупреждения о риске опоздания с отметкой времени обновления. Устаревшую или отсутствующую геопозицию не выдавать за точную.
<a id="f07-r06"></a>
- **F07-R06.** Переназначение при отказе/недоступности курьера; видимый сценарий «подходящего курьера нет». Ручное управление остаётся доступным.
<a id="f07-r07"></a>
- **F07-R07.** Выбор картографического/маршрутного провайдера и стоимость обращений — решение следующего этапа. Не обещать математически оптимальный маршрут без согласованного критерия.

**Критерии приёмки**

<a id="f07-a01"></a>
- [ ] **F07-A01.** Недоступный или перегруженный курьер не назначается вопреки установленным правилам.
<a id="f07-a02"></a>
- [ ] **F07-A02.** Конкурирующие действия оператора и автоматики не создают двойного назначения.
<a id="f07-a03"></a>
- [ ] **F07-A03.** Диспетчер может понять причину назначения и безопасно изменить его.
<a id="f07-a04"></a>
- [ ] **F07-A04.** При отказе маршрутизатора остаётся ручной сценарий; ETA обозначен как недоступный/устаревший.
<a id="f07-a05"></a>
- [ ] **F07-A05.** Полевой сценарий нескольких заказов подтверждает соблюдение ограничений, а не только отображение маршрута на карте.

**Где появится в продукте.** Диспетчерская; настройки автоназначения; маршрут курьера; журнал решений.

**Зависимости.** Готовность заказа и F03; достоверные курьерские статусы/геопозиция.

**Где посмотреть и что изучить**

- [STARTER Логист](https://starterapp.ru/logist) — Посмотреть автоназначение, батчинг, маршруты и работу курьера; рекламные показатели экономии не переносить в обещания Delivest.
- [Смартомато: автораспределение](https://help.smartomato.ru/hc/user-guide/articles/auto-dispatch) — Изучить ограничения нагрузки, режимы распределения и будущие заказы.
- [Смартомато: отслеживание](https://help.smartomato.ru/hc/user-guide/articles/courier-tracking) — Посмотреть отображение статуса и информации доставки гостю.

<a id="f08"></a>
**8. F08 — Комбо-конструктор и пицца из половинок**

**Цель.** Дать пиццериям и заведениям с наборами корректный путь от конфигуратора до кухни и ресторанной системы.

**Что уже есть / что проверить.** Варианты товаров, группы модификаторов и промо уже есть. Специализированные половинки и конфигурируемые наборы ранее не обнаружены; не подменять существующие модификаторы новым параллельным механизмом.

**Основной сценарий.** Гость выбирает размер и две совместимые половины пиццы либо наполняет комбо из разрешённых групп; видит доплаты и окончательную цену.

**Функциональные требования**

<a id="f08-r01"></a>
- **F08-R01.** Настройки наборов: группы выбора, допустимые товары/варианты, минимальное и максимальное количество, обязательность и доплаты.
<a id="f08-r02"></a>
- **F08-R02.** Половинки: общие размер/основа, допустимые сочетания, выбранные половины, политика добавок. Формулу цены определить явно: фиксированная, доплаты или иной согласованный вариант.
<a id="f08-r03"></a>
- **F08-R03.** Показывать итоговый состав и изменение цены до добавления в корзину. Сервер пересчитывает стоимость и проверяет доступность.
<a id="f08-r04"></a>
- **F08-R04.** Учитывать стоп-лист каждого компонента. Если компонент исчез, объяснить замену; не подменять состав молча.
<a id="f08-r05"></a>
- **F08-R05.** Сохранять снимок выбранного состава в заказе, чтобы изменение меню не меняло историю. Повтор заказа проверяет текущую доступность и цены.
<a id="f08-r06"></a>
- **F08-R06.** Передавать состав в кухню, POS и интеграцию так, чтобы персонал мог приготовить заказ. Для неподдерживаемого адаптера явно ограничить функцию или использовать заранее согласованное сопоставление.
<a id="f08-r07"></a>
- **F08-R07.** Проверить сочетание с акциями/бонусами, отменой и возвратом. Не выводить поддержку комбо во всех внешних каналах из поддержки на собственной витрине.

**Критерии приёмки**

<a id="f08-a01"></a>
- [ ] **F08-A01.** Нельзя оформить набор без обязательной группы или с недопустимой комбинацией.
<a id="f08-a02"></a>
- [ ] **F08-A02.** Цена на витрине, в корзине, заказе и передаче во внешнюю систему совпадает по согласованным правилам.
<a id="f08-a03"></a>
- [ ] **F08-A03.** Кухня получает однозначный состав, включая половины и добавки.
<a id="f08-a04"></a>
- [ ] **F08-A04.** Стоп-лист компонента и повтор старого заказа корректно объясняются гостю.

**Где появится в продукте.** Каталог → Конструктор набора/половинок; карточка товара; корзина; карточка кухни.

**Зависимости.** Каталог, модификаторы, цены, стоп-листы и возможности адаптеров F06.

**Где посмотреть и что изучить**

- [ReStar](https://restarapp.com/) — Посмотреть заявленные конструкторы и половинки; детали формулы цены Delivest согласовать отдельно.

<a id="f09"></a>
**9. F09 — Печать и устойчивость рабочего места при сбоях связи**

**Цель.** Дать персоналу понятное состояние печати и восстановление работы после сетевого сбоя; не терять действия и не заявлять неподтверждённый офлайн.

**Что уже есть / что проверить.** POS и кухня уже есть; облачная фискализация не равна локальной аппаратной печати. Аппаратная печать и полноценный офлайн ранее не обнаружены. Этот пункт требует особенно аккуратного разделения объёма.

**Основной сценарий.** Кухонное задание отправлено на принтер, связь прервалась. Сотрудник видит неопределённый результат и может выполнить контролируемую повторную печать, не создавая новый заказ.

**Функциональные требования**

<a id="f09-r01"></a>
- **F09-R01.** Разделить типы документов: кухонный талон, нефискальная информация и фискальный чек. Не выдавать обычную распечатку за фискальный чек.
<a id="f09-r02"></a>
- **F09-R02.** Сначала выбрать поддерживаемое оборудование/подключение и пилотный сценарий. Затем определить точку печати и шаблоны по филиалам/станциям.
<a id="f09-r03"></a>
- **F09-R03.** Очередь печати со статусами ожидания, отправки, подтверждения при возможности оборудования, ошибки и неопределённого результата. Учитывать число попыток и время.
<a id="f09-r04"></a>
- **F09-R04.** Контролируемая повторная печать с пометкой копии, правом доступа и журналом. Доставка задания не означает физическую печать, если принтер не даёт подтверждения.
<a id="f09-r05"></a>
- **F09-R05.** При потере связи интерфейс показывает её состояние и время последнего обновления. Запретить ложное сообщение об успешном сохранении неподтверждённого действия.
<a id="f09-r06"></a>
- **F09-R06.** Первый этап устойчивости — переподключение, восстановление экрана и безопасный повтор подтверждённых сервером операций. Полный офлайн-приём заказов — отдельный подэтап после проектирования синхронизации.
<a id="f09-r07"></a>
- **F09-R07.** Для полного офлайна отдельно решить конфликты номеров/статусов, устаревшие цены и стоп-листы, доступные способы оплаты, синхронизацию и поведение внешних систем. Не обещать офлайн-онлайн оплату.
<a id="f09-r08"></a>
- **F09-R08.** Резервный рабочий процесс при недоступности принтера/сервера описать для сотрудников и проверить на пилоте.

**Критерии приёмки**

<a id="f09-a01"></a>
- [ ] **F09-A01.** Отключение принтера отображается как проблема, не как успешная печать.
<a id="f09-a02"></a>
- [ ] **F09-A02.** Переподключение не создаёт новый заказ и не запускает неконтролируемую повторную печать.
<a id="f09-a03"></a>
- [ ] **F09-A03.** При обновлении вкладки очередь и история доступны авторизованному сотруднику.
<a id="f09-a04"></a>
- [ ] **F09-A04.** Нет сети → интерфейс ясно показывает неподтверждённые действия; восстановление не теряет и не удваивает их в согласованном сценарии.
<a id="f09-a05"></a>
- [ ] **F09-A05.** Приёмку аппаратной печати проводить на выбранной модели оборудования; без неё пункт не считать завершённым.

**Где появится в продукте.** Настройки печати; очередь заданий; индикатор связи POS/кухни; действия повторной печати.

**Зависимости.** POS, кухня, события заказа, права. Выбор оборудования и границы полного офлайна остаются открытыми решениями.

<a id="f10"></a>
**10. F10 — Сохранённый способ оплаты**

**Цель.** Сократить повторное оформление для постоянных гостей без хранения карточных реквизитов в Delivest.

**Что уже есть / что проверить.** Онлайн-оплата и повтор заказа уже есть. Сохранённый платёжный метод ранее не обнаружен. Поддержку конкретных типов методов и сценария сохранения нужно проверить по документации используемого провайдера на этапе проектирования.

**Основной сценарий.** Гость по собственному выбору сохраняет поддерживаемый способ оплаты у провайдера, затем выбирает его при новом заказе и подтверждает конкретную покупку.

**Функциональные требования**

<a id="f10-r01"></a>
- **F10-R01.** Явное согласие на сохранение. Доступность опции зависит от возможностей провайдера и конфигурации продавца; отсутствие опции не мешает обычной оплате.
<a id="f10-r02"></a>
- **F10-R02.** Хранить только разрешённый идентификатор провайдера и безопасные отображаемые сведения. Не хранить PAN/CVV и не включать их в журналы.
<a id="f10-r03"></a>
- **F10-R03.** Кабинет клиента: список сохранённых методов, выбор основного, удаление/отвязка. Проверять владельца метода и область продавца; метод одного продавца нельзя автоматически применять у другого.
<a id="f10-r04"></a>
- **F10-R04.** В оформлении показывать выбранный метод, итоговую сумму и явное действие подтверждения оплаты. Не включать автоматические списания без действия клиента.
<a id="f10-r05"></a>
- **F10-R05.** Обрабатывать недоступный/отозванный метод, дополнительное подтверждение, отказ и возврат к обычной платёжной странице без потери корзины.
<a id="f10-r06"></a>
- **F10-R06.** Повтор запроса и вебхука не создаёт двойного списания; результат оплаты согласован с заказом.
<a id="f10-r07"></a>
- **F10-R07.** Удаление метода не разрушает историю платежей и возможность возврата по уже состоявшейся операции.
<a id="f10-r08"></a>
- **F10-R08.** Сохранённый метод оплаты — отдельная покупка по действию клиента. Подписки, регулярные платежи и тарифы в этот пункт не входят.

**Критерии приёмки**

<a id="f10-a01"></a>
- [ ] **F10-A01.** Без согласия метод не появляется в списке; чужой идентификатор метода недоступен.
<a id="f10-a02"></a>
- [ ] **F10-A02.** Повторная покупка проходит с доступным методом, отказ позволяет выбрать альтернативу.
<a id="f10-a03"></a>
- [ ] **F10-A03.** Двойное нажатие/повтор уведомления не создаёт два платежа за одну операцию.
<a id="f10-a04"></a>
- [ ] **F10-A04.** После отвязки метод недоступен для новых покупок, история и возврат сохраняются.
<a id="f10-a05"></a>
- [ ] **F10-A05.** Проверки проводятся в тестовом контуре провайдера; production-готовность подтверждается отдельным контролируемым сценарием.

**Где появится в продукте.** Личный кабинет → Способы оплаты; оформление заказа; настройки платёжного провайдера.

**Зависимости.** Текущая интеграция оплаты, идентификация клиента, идемпотентность и модель продавца.

**Где посмотреть и что изучить**
