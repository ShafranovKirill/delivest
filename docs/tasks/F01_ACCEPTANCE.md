# F01 — контракты и приёмка реализации

Основа: PR root #34 / server #30 / agent #7. Продолжение отдельно: root/server `codex/f01-marketing-policies`, client `codex/f01-notifications`. Владелец разрешил реализацию и коммиты; merge значительной фичи и production отдельно.

## Контракты

- Независимые контексты Segments → Marketing → Notifications. Reward — существующие Promo/Loyalty, не новый баланс или движок скидок.
- Feature keys — строки `segments`, `marketing_policies`, `notifications`. Политики требуют Segments/Notifications. Включение зависимостей атомарно, отключение затронутых функций с подтверждённым preview. Все locks gate-строк в едином порядке.
- Один общий Background planner, ограниченные пачки/курсоры. Выдачи и внешние эффекты сохраняют прогресс идемпотентно; чистые аналитические расчёты можно начать заново. Никаких дополнительных cron на политику/филиал.
- Issue уникальна по policy/client/completed-order cycle. Возврат/истечение срока/редактирование политики не разрешают повторную выдачу за тот же цикл. Новый completed заказ — новый цикл; повторное completed того же заказа не новый цикл.
- Уточнение владельца 10 ноября: только завершённые заказы «везде». Незавершённый/отменённый заказ не меняет количество, давность, выручку или цикл и не скрывает предложение. Завершение заказа и выдача сериализуются на клиенте. Отмена не разрешает дубликат уже выданной награды за прежний цикл.
- Первый запуск: текущая аудитория либо будущие участники. Future-only фиксирует исходную eligible cohort, а не проверяет дату регистрации клиента. Перед активацией видны охват, область и затраты/неизвестные значения.
- Reward, issue и notification intent создаются одной транзакцией. Только реально вставленная уникальная Issue разрешает финансовый эффект. Недоступность канала не отменяет награду и не создаёт повторную выдачу.
- Изменение используемого сегмента показывает активные политики и требует подтверждения актуального impact + ожидаемой revision. История сохраняется, меняются будущие оценки.
- Notifications API принимает стабильный idempotency key выдачи; source callback проверяет актуальность предложения при показе/отправке. Внешняя доставка в отдельной ограниченной notifications queue; общий аналитический slot не ждёт HTTP.
- Все клиентские уведомления используют общий transport/модуль, но существующие transactional/account события не зависят от маркетингового consent и необязательного планировщика.
- Каналы: in_app, Push, SMS. SMS не подключён, это честное unavailable состояние. Добровольные marketing Push/SMS default off. Клиентская страница «Каналы оповещения», предложения под хедером одновременно с активным заказом. Закрытие только на текущем устройстве, не отменяет бонус/код.

## Доказательства до завершения

- [x] Изоляция франшизы/филиалов и клиентов; скрытые функции/права; выключенный модуль не создаёт задач и необязательных данных.
- [x] Независимые DB connections: конкурентная выдача даёт ровно один код/ledger entry; completed-order race не выдаёт устаревшую мотивацию.
- [x] All-current/future-only, исключения, пауза/повторный запуск, новый цикл, истёкшая мотивация, stale segment edit/impact.
- [x] No provider/no consent/permission denied честны; нет live sends и выдуманного delivered. Unknown external outcome не повторяется вслепую.
- [x] Device A dismiss не скрывает B; просмотр не dismiss; expiry/current-cycle; поздний ответ после logout/branch switch не меняет новую identity.
- [x] Отчёт показывает факты и явное окно атрибуции, не обещает прирост; агрегаты не удваивают выручку. Полная воронка F04 отдельно.
- [x] Новый UI: мастер политики, редактирование черновиков/состояния/отчёт, каналы клиента, карточки + активный заказ, существующие языки/темы.
- [x] Целевые проверки, миграции fresh/down-up, независимое ревью; финальный server precommit1536/0, Dialyzer, клиентские проверки, agent25/25 и OpenAPI snapshot.
- [ ] Remote CI и ревью владельца перед интеграцией в develop. Актуальный статус — на PR; production отдельно.
