# S3 — восстановление, очереди и совместимость

## База

Продолжение [первого checkpoint S3](S3_CHECKPOINT.md) в ветках `codex/s3-recovery-contracts`. Рабочие деревья перед началом чистые, выполнен fetch. Предыдущие PR server №22, client №15 и root №21 прошли GitHub CI и merged в develop. База продолжения — root `3468fe4`, server `076f0a6`, client `9273e56`. Следующий checkpoint закрепляет фактическое восстановление обработчиков и измерения очередей.

## Профиль очередей до запуска

Тестовый стенд использует PostgreSQL и реальные Oban producers/consumers. Базовая интенсивность — эквивалент 50 заказов в минуту для пяти филиалов на протяжении 120 секунд. Всплеск — пятикратная интенсивность 30 секунд. В maintenance создаётся отдельная медленная очередь. Провайдеры заменены локальными mocks с задержкой, 429/503 и неизвестным исходом. Три повторения сохраняют профиль и пороги.

Исходные технические пороги стенда выбраны перед запуском. P95 ожидания готовой задачи в критических очередях — до 2 секунд на базе и до 10 секунд на всплеске. Медленная maintenance может добавить не более 2 секунд к P95 критической очереди. Остаток готовых задач должен обработаться за 60 секунд после окончания инъекции. Эти критерии относятся к измеренному профилю и окружению. Договорные SLA production определяются после замеров целевого сервера и лимитов провайдеров.

## Совместимость

[ADR](ADR-S3-MOBILE-COMPATIBILITY.md) задаёт версию клиентского контракта, правила additive changes и предложенное окно поддержки 180 дней после объявления deprecation. Native-клиент получает те же use cases, ownership и checkout guarantees. Сервер сообщает реальные capabilities. Текущий WebPush и будущие APNs/FCM отражаются отдельно.
