## Профиль очередей до запуска

Тестовый стенд использует PostgreSQL и реальные Oban producers/consumers. Базовая интенсивность — эквивалент 50 заказов в минуту для пяти филиалов на протяжении 120 секунд. Всплеск — пятикратная интенсивность 30 секунд. В maintenance создаётся отдельная медленная очередь. Провайдеры заменены локальными mocks с задержкой, 429/503 и неизвестным исходом. Три повторения сохраняют профиль и пороги.

Исходные технические пороги стенда выбраны перед запуском. P95 ожидания готовой задачи в критических очередях — до 2 секунд на базе и до 10 секунд на всплеске. Медленная maintenance может добавить не более 2 секунд к P95 критической очереди. Остаток готовых задач должен обработаться за 60 секунд после окончания инъекции. Эти критерии относятся к измеренному профилю и окружению. Договорные SLA production определяются после замеров целевого сервера и лимитов провайдеров.

## Совместимость

[ADR](ADR-S3-MOBILE-COMPATIBILITY.md) задаёт версию клиентского контракта, правила additive changes и предложенное окно поддержки 180 дней после объявления deprecation. Native-клиент получает те же use cases, ownership и checkout guarantees. Сервер сообщает реальные capabilities. Текущий WebPush и будущие APNs/FCM отражаются отдельно.

Первый диагностический запуск с 200 maintenance jobs остановлен до завершения. Его профиль требовал 300 секунд работы при concurrency 1 и не мог уложиться в объявленный общий срок опустошения после 150 секунд подачи нагрузки. Итоговые три прогона используют заранее записанный ограниченный профиль 120 jobs по 1,5 секунды. Порог опустошения 60 секунд сохранён. Контрольный этап без maintenance длится 30 секунд и используется для сравнения задержек.

## Устройство восстановления

Событие и задачи подписчиков получают запись доставки по паре event/subscriber. Локальные изменения подписчика и отметка `delivered` фиксируются в одной транзакции. После остановки до commit обе части откатываются. После commit повтор задачи видит сохранённую отметку и пропускает локальный эффект.

Для очередности используется последовательность PostgreSQL. UUIDv7 с обычной точностью миллисекунд содержит случайную часть и не определяет порядок быстрых событий. Запись событий сериализуется по aggregate, обработка — по aggregate и подписчику. Позднее событие ждёт незавершённое раннее. При миграции учитываются существующие задачи Oban. События из архива без сохранённой задачи заново не ставятся в очередь.

CRM create и команды получают сохранённую фазу внешнего вызова. Активный вызов защищён ограниченным lease. Потерянный ответ провайдера без безопасного повтора требует сверки. Последующие команды заказа ждут разрешения неизвестного исхода, чтобы обновления применялись последовательно. Для автоматического создания курьерской доставки устойчивый ключ операции связан с событием и сохраняется при повторе после отката локальной транзакции.

Операторская страница находится по пути `/staff/b/:branch/integrations/recovery`. Списки ограничены текущим филиалом и требуют `orders.update`. Подтверждение выполнения и повтор — отдельные действия с явным подтверждением. Диагностические записи сохраняются независимо от удаления старых Oban jobs. Все решения проверяются application API с правами актёра и филиала.

## Миграции и финансовая история

Главный агент создал отдельную БД на миграции 17, добавил старую бонусную проводку, событие без задачи, завершённую и ожидающую задачи, а также задачу с некорректным UUID. Миграции 18–21 применились. Архивное событие не получило новую доставку, завершённая задача получила `delivered`, ожидающая — `pending`. Последовательность сохранённых задач восстановилась по их реальному порядку постановки, несмотря на обратный порядок UUID. Старая проводка сохранила сумму 10, остаток 10 и получила cycle 0. Следующее новое событие получило sequence 4. Лог `/tmp/delivest-s3r-migration.log`.

Rollback миграций 21 и 20 на данных без новых циклов, затем повторный upgrade прошли. После добавления второго цикла попытка вернуть старую уникальность проводок была отклонена PostgreSQL. Транзакция rollback сохранила обе строки и индекс циклов. Лог `/tmp/delivest-s3r-migration-blocked-rollback.log`. Возврат приложения после появления новых циклов требует совместимой сборки. Старый reader, рассчитывающий на единственную строку начисления на заказ, использовать нельзя.

Восстановление бонусов ведётся дополнительными проводками. После начисления 10, траты 6 и снятия остатка 4 повторное завершение восстанавливает 4. История сохраняет прежние суммы. Если заказ был отредактирован и связан с другим клиентом, восстановление и снятие бонуса остаются у владельца исходного начисления. Автоматического переноса бонуса между клиентами нет.

Сырые результаты и конфигурация сохранены в [s3-queue-results.json](support/s3-queue-results.json), воспроизводимый запуск — [s3-queue-load.exs](support/s3-queue-load.exs). Для повторов она включает время завершения первой неуспешной попытки, поэтому завышает ожидание. ## Порядок поставки и отката

Перед миграциями 18–22 приостановить новые операции, дождаться завершения активных старых worker и остановить все старые writers/consumers. Сохранить перечень незавершённых и неизвестных внешних операций. Затем применить миграции, запустить новую сборку и проверить очереди и страницу восстановления. Параллельная работа старой и новой схемы обработки событий не входит в проверенный rollout.

Старые задачи без попыток сохраняют ожидающую доставку. Завершённые получают отметку выполнения. Уже начатые старой версией задачи с неизвестным исходом требуют сверки до повтора — прежний курьерский обработчик мог отправить запрос с другим ключом до потери локальной транзакции. Архивные события без сохранённых задач не переигрываются.

Для возврата приложения сохранять расширенную схему, данные команд и записи доставок. Сначала остановить новые writers и обработать либо явно сверить оставшиеся внешние операции. Сборка для отката должна понимать новые циклы бонусов. Обычный запуск старого reader после появления нескольких циклов на заказ нарушает его прежнее предположение об уникальности записи начисления. Проверка production rollout и live sandbox остаётся release gate из main.

## Браузерная интеграция

Первый итоговый Playwright дал **26 passed, 1 failed**; pickup упал повторно. БД уже хранила `preparing`, но LiveView продолжал показывать `accepted`. Kitchen subscriber вызывал вложенный status change, который публиковал уведомление до commit внешней транзакции Delivery. Отдельное соединение LiveView читало прежнее состояние; повторного уведомления после commit не было. Этот прогон не считается успешным. Исправление сохраняет атомарность ledger и откладывает уведомление до успешного commit, перечитывая актуальный заказ. Лог исходного сбоя `/tmp/delivest-s3r-main-e2e.log`.

Публикация перечитывает актуальную строку заказа под короткой блокировкой и отправляет только локальные PubSub сообщения. Внешнего HTTP под этой дополнительной блокировкой нет. Возврат API сохраняет исходный результат перехода. Если процесс остановлен между commit ledger и отправкой уведомления, повтор уже выполненной доставки должен заново отправить безопасную инвалидацию состояния, сохраняя запрет повторного эффекта. Socket остаётся сигналом: после reconnect клиент восстанавливает состояние через REST. Дополнительные чтения уведомлений не входят в исторический SQL baseline S1; production профиль критического пути нужно перемерить перед capacity-приёмкой.

Первый полный прогон исправления уведомлений: **1426 tests, 28 failures, 7 excluded**, лог `/tmp/delivest-s3r-main-precommit-final.log`. Причина — возврат `Notifier.publish` потерял прежний preload associations, используемый CRM и аудитом. Исправление сохраняет исходные scalar-поля результата и прежние force-preloaded связи; опубликованный payload по-прежнему берётся из текущей строки БД. Этот промежуточный прогон не считается успешным.
