## Финансовые исправления

- **D07** (`b31dbed`). Расчёт курьера сериализуется в PostgreSQL по филиалу и курьеру. Суммы и количество заказов вычисляются из тех же заблокированных платежей, которые привязываются к проводке. Новое поступление за пределами выбранного набора попадёт в следующий расчёт. Несовпадение количества обновлённых строк откатывает проводку. Повтор без новых платежей возвращает `nothing_to_settle`.
- **D13** (`b3f814d`). Сверка завершает сравнение только после страницы без `next_cursor`. Предел в 50 страниц с оставшимся курсором, повтор курсора и некорректная страница дают `reconcile_incomplete` и метрику `incomplete`. Для частичной выборки сверка пропускает сравнение и автоматическое исправление статусов. Детерминированно неполная выборка отменяет текущий job до следующего планового запуска. Транспортные ошибки идут по обычной политике повторов.

## Оформление заказа

`Oms.Checkout` принимает разрешённые поля, проверенную личность и cookie сессии. UUID в `Idempotency-Key` связан с владельцем, филиалом и отпечатком разрешённого запроса. Ключ фиксируется вместе с заказом, оплатой, списанием звёзд, использованием промо и событиями. Конкурентный запрос ждёт завершения операции и читает тот же заказ. Изменённый запрос с использованным ключом получает `409 idempotency_conflict`.

Ревизия корзины связывает состав, контекст и версию каталога. Checkout проверяет её на том же наборе строк, который использует для расчёта заказа. При расхождении или конкурентной блокировке строк корзины API отвечает `409 cart_changed`. Старые клиенты могут опускать ключ и ревизию.

Сопоставимый замер общего пути заказов после изменения — 32 SQL/заказ, p50 20,57 мс, p95 24,95 мс, 300 заказов сохранены. Чтение корзины добавило один запрос для сверки состава с кешем (1 → 2 SQL, p95 0,33 → 0,48 мс). Мутация корзины осталась на 9 SQL. Логи `/tmp/delivest-s3-{base,after}-{order,cart}.log`.

## Доставка уведомлений и очереди

D10 (`4e7fac9`) фиксирует marker, записи устройств и Oban jobs в одной транзакции. Подтверждённые устройства сохраняют `delivered`, 404/410 удаляет подписку. 429/5xx повторяются до трёх попыток. Transport timeout и незавершённый `sending` переходят в `unknown` с ID для разбора. Автоматический HTTP retry отключён. Повтор job пропускает подтверждённые устройства. Следующий ежедневный запуск отмечает зависшие `sending`, в том числе после сбоя последней попытки. Старые marker-строки сохраняют дедупликацию. Просроченные напоминания получают `expired`.

R04 (`dfe003d`) выделяет `notifications: 2`, `polling: 2`, `maintenance: 1` из прежнего бюджета `default: 10`, оставляя `default: 5`. CRM, events и fiscal сохраняют свои лимиты. Dashboard показывает количество готовых задач и возраст самой старой задачи, включая нули после опустошения очереди. Числа задают исходную конфигурацию. Производственный SLA, provider rate limits и профиль перегрузки требуют отдельного замера.

## Граница приёмки и продолжение

D07/D10/D13 реализованы. R02 реализован для public checkout с совместимым fallback старых клиентов. R01 применён к application facade checkout. R03 подтверждён для атомарной постановки order events и новой доставки expiry, R04 получил изоляцию и backlog, R08 — ключи, версии корзины и drift gate.

Сквозные R01/R03/R04/R08 остаются **partial**. Для полного закрытия нужны проверка всех CRM/fiscal/subscriber unknown outcomes и порядка aggregate events при kill/restart, нагрузочная настройка очередей, operator manual-resolution flow и согласованное окно совместимости мобильного клиента. Перенос всех старых LiveView bulk-транзакций и полный RN lifecycle в этом PR не выполнены. R05 завершён на уровне ADR, реализация требует отдельного решения по перечисленным в нём условиям. Следующий S3 checkpoint должен закрыть эти пункты перед объявлением всего блока завершённым.

## Миграция и возврат

При rollout сначала применить миграции 16–17, затем завершить старые writers/expiry workers и запустить новую сборку сервера с прежними и новыми очередями. Старые Oban jobs сохраняют свои queue и имена worker, прежние очереди должны работать до drain. Клиент обновляется после сервера. Существующие orders без ключа и старые notice-marker не переписываются.

Возврат на старую сборку требует остановки новых producers и drain новых очередей текущим совместимым worker. Сохранять таблицу deliveries, pending/unknown строки и поля ключей до сверки. Автоматический schema downgrade удаляет эти данные, поэтому для rollback приложения сохранять расширенную схему. После downgrade приложения endpoint перестанет поддерживать keyed retry. Production rollout и live-provider sandbox проверки относятся к следующему release gate.
