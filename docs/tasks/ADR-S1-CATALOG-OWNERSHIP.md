# ADR S1: ownership каталога и филиальные полномочия

Дата: 2026-11-06. Автор решения: GPT-6.1 Sol (главный агент), запись: code worker. Статус: утверждено главным агентом.

## Контекст и решение D01–D03

`Product` и `Category` остаются общими записями со связями `Branch` в `entity_relations`. Их нельзя клонировать или удалять при миграции. Изменение общего поля требует соответствующего permission на **каждом** связанном филиале. Изменение orphan записи разрешено только `admin`. Авторизация проверяется до побочных эффектов; bulk, order, delete, import и snapshot writers обязаны использовать ту же границу. Все затронутые филиалы получают инвалидацию каталога и broadcast. Филиальные связи, остановки и CRM IDs остаются филиальными. Для создания CRM ID общей записи филиал должен быть указан явно; первый филиал не выбирается.

Публичное меню и экспорт выбирают товары через связь `Branch → Product`, даже если категория общая. Стопы используют ключ `(branch_id, product_id, source)`; существующий `branch_id` сохраняется. CRM IDs используют ключ `(entity_type, entity_id, branch_id, provider)`; уже записанные mappings и `branch_id` сохраняются. Перед миграцией нужен read-only отчёт о `NULL branch_id`, дублях, ссылках стопов без нужной связи и коллизиях старых ключей при откате. При откате, который объединил бы филиальные стопы или CRM IDs в один старый ключ, операция прерывается, а не удаляет данные.

## Решение D04

`ModifierGroup`, `Modifier` и `ProductTag` остаются installation-global. Для изменения их общих полей вводится `catalog.global.manage`. `admin` получает его через существующую универсальную ACL; филиальным preset ролям capability не добавляется. Чтение остаётся прежним. Привязка модификатора к Product требует `products.update` на всех филиалах этого Product; филиальный CRM ID требует явного `branch_id` и соответствующего филиального permission. Импорт глобальных tags/groups/modifiers через snapshot требует `catalog.global.manage` до побочных эффектов.

`Client` остаётся installation-global. Существующие `clients.read`, `clients.create`, `clients.update` и `clients.delete` трактуются как installation-global capabilities; членство в филиале не сужает их область. Сотрудник без соответствующего permission не читает/не пишет, read-only сотрудник не меняет данные. Политику privacy/read и CRM workflows не менять в S1; она относится к S2 D08.

## Альтернативы и последствия

Клонирование shared записей по филиалам изменило бы идентификаторы и ссылки заказов; отклонено. Выбор первого филиала для полномочий оставляет доступ к чужой общей записи; отклонён. `catalog.global.manage` сохраняет возможность явного назначения installation-wide роли без неявного расширения филиальных permissions. Admin-only для Client отклонён из-за существующих CRM workflows; их явно глобальные permissions сохраняются.

## Rollout и rollback

Сначала отрицательные тесты и отчёт конфликтов, затем новые индексы стопов/CRM IDs и application code. Не удалять `branch_id`. Откат индексов допускается только при отсутствии cross-branch коллизий старых `(product_id, source)` и `(entity_type, entity_id, provider)`; иначе оставить новую схему и остановить rollback для ручного решения. Удаление старых unique индексов несовместимо со старым application writer: нужен координированный deploy без старых concurrent writers, это не zero-downtime migration.
