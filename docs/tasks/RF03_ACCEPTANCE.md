# RF03 — единая статистика: локальная приёмка

**Статус исходной RF03 ветки:** локальная реализация принята главным агентом. Приведённые ниже адресные и браузерные проверки относятся к исходной ветке до объединения RF01–RF04; результаты объединённой версии проверяются отдельно. Данные измерений получены на одноразовом клоне демонстрационной БД, это не production SLA. При объединении миграция RF03 перенесена на `20261210000058_add_refund_sales_rollup_dirty.exs`, поскольку `20261210000056_add_printing_settings_to_branch_info.exs` уже применена в production.

## Методика и контракт

- `Delivest.Analytics.Overview.read/4` авторизует сеть или филиал и ограничивает период 366 локальными днями. Продажи учитывают завершённые заказы; успешные возвраты уменьшают выручку дня исходного заказа. Поздний возврат помечает опубликованный дневной агрегат устаревшим; фонова́я перестройка публикует исправленную сумму. Пока идёт перестройка, возвращаются прежние значения, исходный `updated_at` и `state: :partial`.
- Сеть складывает аддитивные дневные показатели по доступным филиалам. Уникальные клиенты считаются по проверенной идентичности во всей выбранной области, включая историю до периода для определения новых/возвратившихся; неизвестные гости не превращаются в новых клиентов. Неполное покрытие скрывает клиентские числа. Для сравнения предыдущий период обрезается по тому же локальному времени текущего дня и имеет собственное состояние полноты.
- Серверные детали и F04 отчёты нормализуют исторические значения отключённого источника в `other` до пагинации, группировки и фильтрации. Выручка остаётся в общих итогах, скрытые метки не выходят наружу. Детали заказов дополнительно требуют `orders.read`. Продукты и категории показывают валовые суммы до возвратов: надёжного распределения возврата заказа по позициям нет.
- Метрика своевременности скрыта: в текущей модели нет надёжной пары обещанного и фактического момента исполнения. Первый опубликованный день требует фоновой сборки; до неё обзор честно сообщает частичное состояние. У сети дни группируются по локальному календарю каждого филиала.

## Браузерная проверка

Проверены четыре сочетания desktop 1440×1000 и mobile 390×844 со светлой/тёмной темой: горизонтального переполнения и ошибок страницы не обнаружено. Проход через сравнение, продажи, продукты, заказы, отмены, возвраты, переключение сеть ↔ филиал с сохранением периода и пустой период прошёл. Замер открытия статистики за 7 дней до подключённого LiveView с видимым обзором в dev Chromium: 30 навигаций на вариант, филиал p50 209.093 мс / p95 296.135 мс, сеть p50 249.356 мс / p95 323.930 мс. Это измерение **только после RF03**; браузерного baseline до новой UI нет.

## Сравнимое измерение

Исходник: `server/scripts/rf03_statistics_benchmark.exs`. Запускать **только** на отдельном клоне `delivest_rf03_bench_*` с `MIX_ENV=dev DEV_DATABASE=... mix run --no-start scripts/rf03_statistics_benchmark.exs`. Скрипт отказывает до старта приложения при другом окружении/имени БД. Клон создан из локальной F01 demo базы (около 2002 заказов). Данные заказов исходной demo базы не менялись; в ней применили миграцию 56 и обновляли кэш. Для каждой строки 30 выборок, p95 — 29-е отсортированное время; SQL считается по repo telemetry. «Cold» очищает process/Cachex кэши, не PostgreSQL buffer cache. Старый путь вызывает `Analytics.summary/daily/hourly/breakdown(fulfillment/payment)`; новый — единый `Overview.read`. Перед замером новый дневной кэш опубликован. **Таблица измеряет только backend read calls: без HTTP, LiveView render и браузерной навигации.** Между путями различается объём деталей, поэтому результаты не являются сравнением тождественных SQL запросов или p95 открытия страницы.
