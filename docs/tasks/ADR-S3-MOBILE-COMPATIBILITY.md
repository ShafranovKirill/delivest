# ADR S3 — Совместимость API с мобильными клиентами

**Решение от 6 ноября 2026 года.** Текущий клиентский API получает явное обозначение контракта `1`. Новые версии сервера сохраняют этот контракт для опубликованных клиентов. Совместимость проверяется на сервере и в CI до поставки изменений.

## Правила изменения

В пределах версии 1 допускаются дополнительные необязательные поля запроса, ответа и событий. Существующие маршруты, обязательные поля, типы, единицы денег, смысл статусов и правила авторизации сохраняются. Клиент игнорирует неизвестные поля и обрабатывает неизвестный код ошибки общим сообщением с возможностью восстановить состояние через API. Новое значение закрытого enum требует проверки старого потребителя или новой версии контракта.

Несовместимое изменение получает версию 2 и параллельный маршрут либо явно согласованный механизм выбора версии. Версия 1 работает минимум 180 дней после опубликованного объявления о прекращении поддержки. Дата окончания поддержки публикуется заранее. При отсутствии такого объявления прекращение поддержки версии 1 не планируется. Это предложенная исходная политика поддержки. Перед первым выпуском мобильного приложения подтвердить её с владельцем продукта и сохранить перечень поддерживаемых сборок.

Сервер сообщает поддерживаемые версии и возможности через `GET /client/capabilities`. Этот запрос создаёт cookie сессии и возвращается с `Cache-Control: no-store`. Нативный клиент выполняет его перед первым запросом корзины или подтверждением телефона. Клиент проверяет возможности перед использованием нового поведения. Передача номера сборки приложения служит диагностике. Сервер не должен разрешать дополнительные права по номеру версии, platform header или User-Agent.

## Оформление и восстановление заказа

Старый клиент может создавать заказ без `Idempotency-Key` и `cart_revision`. Новый клиент получает revision из ответа корзины и сохраняет UUID операции до определённого результата. При потере ответа повторяет тот же запрос с тем же ключом. Ключ ограничен проверенным владельцем и филиалом. `409 cart_changed` требует перечитать корзину и показать новый расчёт. `409 idempotency_conflict` требует найти ранее созданный заказ. `502 payment_unavailable` с ключом допускает повтор исходной операции для восстановления оплаты.

После reload, reconnect или пропущенного socket-события клиент перечитывает активные заказы и нужный заказ по ID. Источник состояния — REST API. Socket служит уведомлением об изменении. Версия envelope событий — 1. Неизвестную версию envelope клиент обрабатывает повторным чтением API. API возвращает целые денежные суммы в копейках, UTC timestamps со смещением и timezone филиала для отображения локального времени.

## Требования к будущему native-клиенту

Нативный HTTP-клиент сохраняет cookie jar установки. Cookie `session_id` требуется корзине и phone-confirmation в дополнение к bearer-токену клиента. Access/refresh-токены хранятся в Keychain/Keystore. При смене пользователя очищаются данные прежней личности, подписки и отложенные callbacks. Выход и повторный вход проверяются на устройстве до выпуска.

Оплата открывается в системном браузере. Возврат через universal/app link используется как сигнал перечитать заказ. Признак успешной оплаты берётся с сервера после проверенного webhook или сверки. Секреты ЮKassa остаются на сервере.

Текущий push-контракт использует WebPush. Поддержка APNs/FCM токенов должна появиться отдельной серверной возможностью с привязкой устройства к владельцу и отзывом при logout. Discovery сообщает фактически поддерживаемый механизм. До реализации native-device API сервер не объявляет поддержку APNs/FCM.

## Проверка и граница

В CI закрепляются baseline контракта версии 1, необязательность checkout additions, стабильные деньги/времена/ошибки, discovery и envelope событий. Серверные и браузерные тесты проверяют ownership, token refresh, повторы заказа и восстановление состояния. Исполнение native secure storage, app links, APNs/FCM и lifecycle на iOS/Android проверяется при создании соответствующего приложения. Этот ADR определяет контракт и требования его выпуска.
