# Эксплуатация парка Delivest

Этап 5 дополняет [ТЗ Delivest SaaS](https://app.notion.com/p/42531ec95e448158be68c332619781dc). Подключение Node и подготовка управляемого релиза описаны в [этапе 3](saas-stage-three.md). Настройка внешнего хранилища, расписания копий и восстановление Bastion описаны в [этапе 4](saas-stage-four.md).

## Обновление франшиз

В «Франшизах» выберите все управляемые установки или нужную группу. Укажите контрольную франшизу. Bastion фиксирует состав, опубликованную версию, адрес пакета и SHA-256 при создании задания. Очередь запускает одну установку за раз, начиная с контрольной. После первой ошибки или неясного результата выдача останавливается. Ручная пауза тоже останавливает выдачу следующих заданий. Текущая команда доводится до результата.

В журнале проверьте статус каждого элемента. После восстановления связи дождитесь сверки с Node по исходному ID операции. При продолжении Bastion сохраняет успешные результаты, повторяет элементы с подтверждённой ошибкой и выдаёт ещё не начатые элементы. Прерывание во время миграции требует сверки по журналам Node и PostgreSQL перед любым повтором.

Обновление запускается также из карточки франшизы или из Telegram. Подтверждение в Telegram закрепляет показанную версию. Повтор подтверждения открывает ту же операцию. Карточка показывает свежесть проверки витрины и API, heartbeat, версии и состояние копии.

Автоматическое обновление требует опубликованный пакет с `managed-upgrade.json` от пройденной проверки предыдущего стабильного релиза. Node сопоставляет установленную версию и SHA сервера с указанной базой. Несовместимая миграция, пропущенный промежуточный релиз и изменение конфигурации PostgreSQL, SeaweedFS или томов требуют отдельного плана обновления. Если сервер не подтверждает завершение миграции, сохраните ID операции и результаты проверок до возобновления. Возврат к прежней схеме требует согласованного восстановления с учётом заказов, поступивших после снимка.

## Наблюдение и обслуживание

Обзор показывает связь с Node и доступность сайтов независимо, свежесть метрик, свободные RAM и диск, сроки TLS и состояние бэкапов. Два подтверждённых отказа сайтов на одной ноде появляются в одном инциденте. При потере heartbeat рабочая витрина остаётся доступной гостям. В журнале сохраняются прошлые инциденты.

Порог пилота для CPU составляет 90%, для свободной RAM 512 МиБ, для диска 5 ГиБ. Метрики считаются устаревшими через 90 секунд, полная копия через 36 часов. Задайте другие значения в переменных `MANAGED_CPU_WARNING_PERCENT`, `MANAGED_RAM_WARNING_KIB`, `MANAGED_DISK_WARNING_KIB`, `MANAGED_METRICS_STALE_SECONDS` и `MANAGED_BACKUP_WARNING_SECONDS`. При выборе ноды интерфейс предупреждает о ресурсах. Режим обслуживания запрещает новые размещения и сохраняет работу текущих. Для доставки оповещений включите `MANAGED_FLEET_ALERTS_ENABLED=true` после проверки канала и получателя.

Node сверяет счётчики перезапусков Docker. После обнаружения трёх перезапусков одного сервиса за пять минут Node отключает для него автоматический перезапуск и передаёт инцидент. Счётчик читается по heartbeat, поэтому между замерами возможно больше трёх попыток. После устранения причины запустите франшизу вручную из её карточки.

## Перенос и аварийное восстановление

1. Включите обслуживание исходного сервера, если переносите с него несколько франшиз. Для каждой завершите перенос отдельно. При плановом переносе остановите выбранную франшизу через Node и дождитесь результата с подтверждением ограждения. Затем создайте полную внешнюю копию и дождитесь проверки целостности. При аварии отдельно оградите исходную ноду на уровне инфраструктуры и укажите в Bastion, как это сделано. Потеря heartbeat сама по себе ограждение не подтверждает.
2. В карточке франшизы выберите «Перенести», укажите другую готовую ноду и свободный loopback-порт. Bastion закрепляет копию, резервирует целевое размещение и выдаёт команды с ID, ревизией и контрольной суммой.
3. Скачайте заверенную копию в закрытый каталог целевого хоста. Выполните `stage-placement-transfer.py` под пользователем службы Node и зарегистрируйте выданное размещение через локальный RPC. Скрипт проверяет контрольную сумму, восстанавливает тома и файлы и оставляет контейнеры выключенными. Сохраните архив защищённым до завершения проверки.
4. Опубликуйте DNS для существующих имён витрины, API, медиа и HTTPS-перенаправлений на адреса целевой ноды. Запустите указанную в Bastion подготовку через `DelivestNode.Transfer.prepare_base64/1`. Она проверяет DNS, включает установку, готовит TLS и маршруты и проверяет витрину, API, админку и публичное и приватное хранилище. DNS переключает оператор.
5. Подтвердите перенос в Bastion после готовности целевой ноды и внешней проверки. Сохраняются ID франшизы, история и прежний URL API. Проверьте заказ и его медиа на новой ноде, перенаправление старого домена и доступность соседних установок. Не включайте исходный проект после того, как новая база начала принимать запись.

## Периодическое восстановление

Bastion может раз в неделю загрузить и проверить последние полные копии. Задайте `MANAGED_RECOVERY_DRILL_SSH_CONFIG` как путь внутри контейнера Bastion к конфигурации с профилем `delivest-recovery-verifier`. Смонтируйте конфигурацию, закреплённые ключи хоста и отдельный ключ доступа с правами чтения только для пользователя Bastion. На отдельном Docker-хосте ограничьте этот ключ принудительной командой `python3 …/priv/verify-recovery-ssh.py` и запретите переадресацию и интерактивную оболочку. На проверочном хосте заранее нужен образ PostgreSQL с digest из верификатора.

По понедельникам в 07:00 по Москве Bastion ставит по одной проверке для каждой актуальной копии. Восстановление работает без сети и без Phoenix, платежей и рабочих фоновых заданий. Проверяются запуск PostgreSQL, схема приложения и байты файлов в томе медиа. Результат записывается в карточку франшизы. Для подтверждения точки восстановления, на которую опирается очистка копий, по-прежнему нужна проверка приложения и связанных объектов.

## Протокол ночной приёмки

Для каждого пункта запишите SHA Bastion и Node, версию пакета Delivest, ноду, ID франшизы и операции, время проверки, ожидаемый и фактический результат.

| Сценарий | Что подтвердить |
| --- | --- |
| Две ноды и несколько франшиз | Изоляция данных, Docker-сетей, учётных данных и команд. |
| Демо и клиентские домены | Запуск, REG.RU и внешний DNS, сохранение пути в редиректе, заказ через прежний API. |
| Потеря управления | Выключение Bastion, переподключение Node, повтор команды и перезапуск хоста. |
| Обновление при сбое | Пауза после ошибки контрольной франшизы, неизменность успешных элементов, повтор после сверки. |
| Отказы DNS и ресурсов | Обзор, просроченный TLS, низкий запас RAM/диска, общий инцидент и одно оповещение. |
| Авария исходной ноды | Из внешней копии восстановлены заказ и медиа, прежний API работает, старая нода ограждена. |
| Обслуживание | Новые размещения запрещены, работающие франшизы продолжают отвечать. |

В локальном Docker-прогоне снимок синтетической установки создался за 13,44 с. После удаления исходного проекта восстановились заказ № 42 и связанные медиа. Соседняя установка отвечала, неверная контрольная сумма была отклонена. Целевое размещение ревизии 2 подготовилось с выключенными контейнерами. Серверная приёмка, REG.RU, переключение публичного DNS и выпуск TLS в этом прогоне не выполнялись.

На синтетических Compose-проектах подтверждены ограждение всех пяти контейнеров исходной установки, её явный повторный запуск и работа соседнего проекта. Docker daemon в этом прогоне не перезапускался. Отдельный сценарий восстановления базы Bastion проверил реестр, размещения, домены, защищённые данные и историю операций.

Локально прошли `mix precommit` в Bastion (259 тестов), `mix test` и Python-тесты Node (37 и 24) и проверки сборки пакета и политики обновления Delivest (по 12 тестов). Архив Node 0.3.0 для Linux x86-64 собран, его состав и контрольная сумма проверены. Пакет Delivest с тестовым отчётом принял валидатор Node. Миграция и переключение обновлённой франшизы на реальной ноде входят в ночную приёмку.
